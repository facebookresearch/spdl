Technique catalog: symptom-indexed candidates¶

The technique catalog brings together practical ways to improve SPDL input pipelines, along with lessons from approaches that did not help. The entries are organized around symptoms you may encounter, so you can find ideas relevant to your workload.

To choose a useful starting point, begin with the analysis guidance: it helps you connect pipeline statistics and profiles to the cost limiting your training. Each entry is a candidate to test when your measurements match its trigger, rather than a checklist to apply in order.

Stable IDs identify screened and tested changes. Each entry explains when it applies, what to change and the checks needed before using it. There is no expected-gain field: compare the candidate with your own baseline. Source links are optional provenance; consult them when implementation, compatibility or correctness details need confirmation, not to copy a past speedup.

Before optimization, establish migration parity by reusing the original components. If the replacement is slower, see Compare loader implementations in the Optimization Guide. A faster path that loses data, changes effective batch or fails numerical/quality gates is not a promotable win. Use SPDL to compose and optimize the input pipeline. Baseline-specific adjustments preserve compatibility with components already in use.

How to use the SPDL references¶

Where a public SPDL utility fits the mechanism, the area entry includes an SPDL reference with an API link or implementation example. These are options to compare with the existing pipeline, not required replacements or promises of a speedup. Check experimental status, the installed API version, data semantics and buffer lifetime before using one. Storage-client, allocator, GC and model-specific changes may still need the existing application’s implementation; the catalog does not invent an SPDL API for them.

How to screen¶

  1. Gather SPDL stage statistics, minimum sink occupancy across all ranks, actual GIL-holder/native stacks, host file/anonymous/swap memory, total worker/thread CPU, per-rank GPU memory, and trainer/boundary timings. A full sink and low fetch wait do not rule out trainer-thread interference. For a containerized job, also read the container’s own memory use and its file/anonymous split against the container limit at each epoch (for example cgroup memory.current and the file and anon lines of memory.stat). A mostly idle host does not rule out memory pressure inside the container.

  2. Use the trigger table to open only matching area files. Read the technique and guards before proposing an entry. When a measured cost has no obvious trigger match, also search the area files for the mechanism you see in profiles (the resource or call, such as page cache, file or handle opens, or buffer copies), not only for the index wording. Triggers name symptoms, and a mechanism may sit under an entry described for a related object. Record such a pick as a match by analogy.

  3. Rule an entry out as already implemented only after checking every clause of its Technique against the pipeline, and name the clauses you checked. An entry can cover more than its title; for example, a cache-residency policy can cover both reads and writes.

  4. Write each picked ID with the matching observation, and each inapplicable ID with the reason, in the campaign record’s technique screening log. If your deployment provides a technique-usage recorder, also record each picked ID there when you decide to test it, and keep the returned usage ID in the log. The screening log is the human-readable record; the recorder is what the catalog maintainers aggregate, and writing one does not replace the other.

  5. Rank candidates by exposed critical-path cost. Test independent hypotheses on separate forks of the validated parent. Preserve data coverage, randomization, checkpoint/resume and batch/update semantics.

  6. Re-profile and compare matched native runs. Count cold preparation, startup, final drains, evaluation/checkpoints and realized resources in the complete-run result; validate quality against the original model baseline. When the attempt reaches a decision, update its screening-log entry and, if you recorded the selection, record the outcome with the same usage ID.

ID to area file¶

The area files explain Trigger (when it may fit), Technique (what to change and why), Guards (correctness and tradeoffs), and an optional SPDL reference. Counterexamples separate the Attempt and Outcome from Guards and when to revisit. If the change was not run, look for Not tested instead of Attempt. Deployment-specific mechanisms and internal source links belong in the deployment source map, not in these shared files.

Maintenance¶

Add a new stable ID only for a distinct mechanism, with a plain-language trigger, concrete intervention and essential safety/quality guards. Merge duplicate support into existing IDs; do not rename them. Keep all organization-specific names and evidence links outside the shared catalog. Explain the input/output representation, concrete intervention and guards so an OSS reader can understand and apply the idea without opening a private source diff; add a small reference example when the mechanism is otherwise ambiguous. Public SPDL API references are options to compare, not required replacements. For counterexamples, separate what was tried from the outcome and conditions for revisiting it; mark unrun proposals as Not tested. Omit historical gain summaries; keep source links as optional provenance rather than required reading.

The index is a shortlist, not the full explanation. In an area entry, explain the usual situation and input representation, why work is repeated or expensive, and how the proposed change removes it. Trigger and Technique can be longer when that makes the reasoning clear to a fresh reader; use a concrete before/after example when helpful. Make Guards follow naturally from that reasoning while retaining unique correctness, lifetime, resource, quality and negative-result checks. Do not replace the explanation with a dense checklist of technical terms.

Keep this entry point screenable: put complete entries in the matching area file and update the ID-to-file table. New model-execution mechanisms belong in the separate model optimization catalog; this input-focused catalog retains its historical input-adjacent entries without duplicating them. Model hypotheses can be investigated alongside input work; use the measured path for attribution and preserve quality gates. Every bundle consuming this index must include the sibling techniques/ and model_techniques/ directories and resolve their relative links.
