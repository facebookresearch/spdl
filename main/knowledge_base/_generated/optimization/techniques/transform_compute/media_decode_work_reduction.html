Media decode work reduction¶

These techniques reduce media decode, metadata and intermediate-buffer work. Open this topic when PCM extraction, per-record timebase conversion, temporary files, demux contention or repeated frame decoding limits delivery.

Catalog index · Transform compute

scalar_timebase_without_fraction_objects: avoid rational-object construction per record

  • Trigger: metadata handling repeatedly constructs rational objects only to obtain a scalar timebase, such as seconds per timestamp tick. Allocating a Fraction for every record is unnecessary when the consumer only uses the corresponding scalar ratio.

  • Technique: compute the required scalar directly from the stored numerator and denominator, avoiding per-record Fraction allocation when exact rational arithmetic is not required by downstream consumers. For a timebase expressed as numerator/denominator seconds per tick, use that ratio at the same scalar-conversion boundary as the baseline, not its reciprocal or a differently rounded intermediate.

  • Guards: preserve timestamp units, rounding and precision at the required boundary. Check zero or invalid denominators and large values; retain the exact path when equality, ordering or seeking depends on rational semantics. Do not replace a correctness requirement with floating-point arithmetic merely because it is cheaper.

zero_copy_raw_wav_window_views: expose PCM windows without general decoding

  • Trigger: in-memory WAV audio already contains raw pulse-code modulation (PCM) sample values, yet extracting a time window still passes through a general demuxer and decoder. For supported raw layouts, the requested samples can be located directly in the data chunk rather than obtained through general decoding.

  • Technique: parse the supported WAV format and data chunks rather than assuming a fixed header length. Convert the requested time window to the baseline’s sample-frame endpoints, locate those frames in the PCM payload, and expose a typed view with the correct channel layout over the backing bytes. For interleaved two-channel int16 PCM, each sample frame occupies four bytes, so frame 100 starts 400 bytes into the data chunk. This avoids demuxing or copying the whole stream; if the consumer requires scaled floating samples, that conversion remains necessary.

  • Guards: validate format, header bounds, sample alignment, channels and window endpoints. Keep the buffer owner alive and route unsupported or inconsistent encodings to the original decoder. Preserve byte order, signedness and the decoder’s amplitude convention; packed formats that lack a compatible view still require conversion. Python array construction can still limit thread scaling after the decode shortcut.

  • SPDL reference: spdl.io.load_wav() accepts in-memory WAV bytes and optional time_offset_seconds and duration_seconds arguments. For supported raw layouts, use numpy.asarray on its result to obtain a zero-copy view shaped (sample_frames, channels) in the stored sample dtype. It does not resample or normalize amplitudes.

decoder_admission_and_stage_split: bound demux separately from hardware decode

  • Trigger: demuxing—the container reader producing encoded packets—takes disproportionately longer as more streams are admitted concurrently. The hardware decoder consumes those packets under a separate session-capacity limit, so admitting more whole-stream tasks can delay packet delivery and leave the decoder starved rather than keep decoding busy.

  • Technique: split encoded input into packet production (demux) and packet consumption (hardware decode), connected by a bounded queue that retains each stream’s order. Set separate limits on active demux tasks and decode sessions instead of treating each whole stream as one task with a single concurrency limit; size decode concurrency to the hardware decoder’s capacity. Sweep demux admission downward when oversubscription increases latency, while keeping enough ordered packet work ready for the hardware’s decode capacity. Demux can also run in a separate process, with packets serialized across the boundary, to keep its CPU work from interfering with device-kernel dispatch. The output remains the requested decoded frames, not the packet queue itself.

  • Guards: maintain packet order, codec dependencies and buffer ownership. Measure queue occupancy and stage latency rather than assuming more demux tasks help; too little demux concurrency also starves the decoder, so sweep for a balance point rather than the minimum. The cause of demux slowdown can be misdiagnosed (for example, contention on a lock inside the demux library rather than memory bandwidth), so measure both stages directly. Attribute gains separately: a winning configuration may also include process isolation of demux, packet serialization and shorter subclips, which are not admission tuning. The best limits are workload-specific, especially for small, short clips where per-item overhead dominates.

  • SPDL reference: use spdl.io.demux_video() in the demux stage to produce encoded video packets, then pass them to spdl.io.decode_packets_nvdec() in the decode stage. This experimental API takes a device_config and returns a GPU buffer; its interface may change, so benchmark it on your workload. Tune the two stages’ concurrency separately.

in_memory_encoded_media_decode: decode encoded buffers without temporary files

  • Trigger: encoded media is downloaded to temporary files and reopened while filesystem I/O is saturated.

  • Technique: pass encoded byte buffers directly to a decoder that accepts memory-backed input, removing the temporary-file write, open and reread round trip.

  • Guards: keep backing buffers alive for asynchronous decode and bound concurrent encoded plus decoded memory. Validate seeking, numerical output and error handling against the file-backed path. An in-memory interface does not automatically provide zero-copy output or remove downstream materialization.

  • SPDL reference: pass the encoded bytes directly to spdl.io.load_image(), spdl.io.load_audio(), or spdl.io.load_video(), as appropriate, instead of writing a temporary file. Benchmark the change independently; avoiding disk I/O does not guarantee higher end-to-end throughput, especially if concurrent demux calls become the bottleneck.

decode_scale_sample_fusion: filter frames before large intermediates escape decode

  • Trigger: full-resolution frames are buffered only to be resized and sparsely sampled afterward.

  • Technique: move the baseline’s resize and frame-selection operations into a supported native decode/filter path, returning only the retained, resized frames plus their required timestamps. Decode codec-reference frames as needed, but do not buffer or convert discarded full-resolution frames into Python-visible arrays. For example, a request for original frame indices 0, 4 and 8 must retain those indices, not take every fourth frame after an earlier filter has renumbered the stream. Match the baseline operation order rather than assuming resize and sampling can always be swapped.

  • Guards: validate interpolation, color and HDR handling, timestamps and sampling order. Measure aggregate CPU time as well as wall time and memory; internal parallelism can shorten latency while using substantially more CPU. Preserve retained-frame content rather than silently reducing the sample set.

  • SPDL reference: use spdl.io.sample_decode_video() with demuxed video packets and sorted, unique frame indices. Use filter_desc to resize within the decode path when that matches the baseline’s operation order. For H.264 it starts new decode groups only at verified IDR packets, preserving earlier dependencies at other keyframes. Filters run within each group, so check that the result matches the baseline if filtering depends on surrounding frames.

bounded_sparse_video_decode_plan: share bounded forward decoding across requests

  • Trigger: sparse frame requests repeatedly seek and decode overlapping portions of the same video.

  • Technique: retain each request’s original position, sort requests by frame position or timestamp, and group nearby requests into bounded forward-decode segments. Seek to a suitable preceding codec entry point, decode forward once per segment, and retain the requested frames. Restore request order and duplicates when returning frames. For requests [10, 3, 10], decoding positions 3 and 10 once can still return [frame 10, frame 3, frame 10]. Split distant requests rather than decoding an arbitrarily long gap; the bound must include dependency frames, not just retained frames.

  • Guards: respect codec dependencies, timestamps, exact pixels and segment ownership. Bound the amount decoded between distant requests; preserve duplicates and random sampling. Separate decoder-plan effects from storage locality, cache warmth and the broader training stack.
