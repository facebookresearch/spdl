# Host dispatch and CUDA replay

These techniques reduce repeated optimizer-state traversal, avoidable host readbacks and dispatch between short GPU kernels. Open this topic when Python optimizer bookkeeping or device verdicts block the enqueueing thread, reporting forces waits, or a stable launch-bound region has gaps between kernels.

**`optimizer_state_traversal_hoisting`: resolve aggregated optimizer state once per update**
- Trigger: CPU profiles show recursive optimizer-state lookup or tensor-keyed dictionary aggregation repeatedly delaying an otherwise unchanged update. For example, a wrapper around several optimizers or sharded state rebuilds a merged mapping from parameter tensors to their state by walking nested optimizers and inserting keys one at a time whenever the step or a hook asks for state. The GPU waits while this Python traversal and tensor-key hashing repeats.
- Technique: Resolve the optimizer's aggregated state once for the update and reuse that mapping. Where dictionary merge semantics match, use bulk dictionary updates rather than Python per-key insertion, avoiding repeated traversal and tensor-key hashing.
- Guards: Scope reuse to a period in which the state mapping cannot change. Preserve duplicate-key precedence, tensor identity, lazy state creation, wrapper ordering and parameter-group membership. Re-resolve after state load or replacement. Check update/checkpoint equality and training quality; do not remove synchronization that state access actually requires.

**`device_gated_optimizer_skip`: gate non-finite updates on device and reconcile host state later**
- Trigger: an optimizer wrapper reads a GPU NaN/Inf verdict with `.item()` after backward and a verdict all-reduce, blocking that thread from enqueueing the next forward.
- Technique: keep the all-reduced verdict on the device and install flag-aware update kernels that suppress parameter and moment writes for skipped steps while still calling the inner step. Copy the verdict asynchronously to pinned host memory with a completion event, and resolve it at the next step or explicit state-read boundary. Snapshot host step, learning-rate schedule and clipping counters before and after the attempted step; on a skip, roll back only values that still equal what that step left, preserving newer host edits. This is a custom kernel-and-wrapper integration, not a general PyTorch optimizer switch; keep it opt-in, with the host-skip path unchanged when it is off. Expect a narrow supported scope: in one tested case, device gating covered only one FP32 fused-Adam variant (decoupled weight decay, version-specific AMSGrad handling, no fully sharded optimizer state) behind an explicit allow-list of wrappers. Route unsupported optimizer chains and gradient accumulation to ordinary host skipping.
- Guards: all ranks must use the same verdict. Zero gradients before every backward: skipped device steps leave NaN/Inf gradients in `.grad`, unlike the host path. Resolve pending verdicts before save, load, explicit step/hyperparameter mutation or state access; preserve loaded/newer host state and invalidate cached kernel pointers when storage is replaced. Skip counts and warnings are deferred until the verdict is read, and skip-limit enforcement occurs only at the next step: a verdict read during save or load is counted but does not raise even if it exceeds the limit. Explicitly consume the final pending verdict. Immediately-after-skip metrics differ: logged schedule values can be one step ahead and the gradient norm can be NaN. Per-step state readers force a wait and can remove the benefit. Keep Adam's step counter on the host with the other rolled-back host state; moving it to the GPU is a different design, not the validated one. Test repeated skips and checkpoint resume bitwise, and measure performance with skipped steps present: a timing comparison without skips does not measure rollback cost, and in one tested case it was not measured.

**`avoidable_host_readback_removal`: remove host reads of device values nothing needs now**
- Trigger: GPU execution pauses while the host reads tiny tensors for unused metadata, debug output or per-step reporting. Calls such as `.item()`, `.tolist()`, `float(tensor)` or printing a device tensor can make the host wait for the work needed to produce/read those values. The calling thread then stops enqueueing further work, but unrelated streams or devices may continue; a host read does not prove GPU-wide idleness.
- Technique: Compute host metadata lazily only on paths that consume it. Remove redundant reads, and move nonessential tensor inspection out of compiled computation. Accumulate detached reporting values on device and read them at an explicit reporting boundary rather than every step.
- Guards: Retain reads that determine the current optimizer update, stopping or safety decision. Preserve metric denominators and reporting semantics; flush pending reports at completion. Do not retain autograd graphs or captured output aliases in a logging buffer. A side stream alone does not remove a required host synchronization.

**`launch_bound_cuda_graph_replay`: replay captured GPU work for launch-bound regions**
- Trigger: A stable GPU computation launches many short kernels and waits on Python, framework or driver dispatch between them. Profiles show gaps between kernels that are longer than the kernels themselves.
- Technique: Warm the capture-safe computation on a side stream and record its GPU work with persistent input/output addresses. Before their next use, explicitly stage new values into the persistent input buffers; raw `graph.replay()` does not accept and copy fresh Python arguments. An autograd-aware wrapper may provide staging, but follow its contract rather than assuming replay performs a copy. Replay writes to the captured output storage. Keep dynamic or host-dependent sections outside substantial safe captured regions, and include backward only through a supported autograd-aware path such as `torch.cuda.make_graphed_callables`. Compiler modes request lower-overhead execution; verify what was actually captured.
- Guards: Preserve addresses, shapes, gradients and replay order. Order producer work before side-stream warmup and warmup completion before recording or replay. Do not overwrite persistent inputs until earlier graph reads finish, or replay over captured outputs until consumers finish or copy them. Python work is not replayed; keep noncapturable schedule/scaler/update logic outside and count warmup updates correctly. Finish lazy initialization, retain resources and verify RNG and resume; rebuild graphs after storage/state replacement. If GC destructors issue CUDA calls, suspend collection only during capture with exception-safe restoration. Measure memory and execution without intrusive profiling.
- Reference: [CUDA graph capture and replay constraints](https://docs.pytorch.org/docs/2.15/notes/cuda.html), [torch.compile / in-place Module.compile](https://docs.pytorch.org/docs/2.15/generated/torch.compile.html). Check the installed framework version; these APIs are options, not requirements or proof that the intended path executed.
