# Compile boundaries and reuse

These techniques select tensor-only compile regions, reuse repeated-block code and register opaque custom-kernel boundaries. Open this topic when mixed wrappers break graphs, repeated blocks inflate cold compilation, or an unsupported implementation interrupts useful surrounding compilation.

[Model catalog](../index.md) · [Compilation, graph replay and host dispatch](../graphs_dispatch.md)

**`tensor_only_compile_regions`: compile tensor-only functions instead of mixed wrappers**
- Trigger: Compiling a large wrapper repeatedly recompiles or falls back to eager because it mixes tensor computation with changing Python metadata. For example, a compiled top-level step that also builds metadata dictionaries, logs values or reads changing Python counters produces graph breaks between small traced pieces and fails guards whenever those Python values change. Compile logging such as `TORCH_LOGS="graph_breaks,recompiles"` shows where and why.
- Technique: Move compilation onto substantial tensor-in/tensor-out functions, such as leaf model blocks or the loss calculation. Keep irregular metadata construction and unsupported host bookkeeping outside those functions. Consolidate unavoidable breaks at boundaries instead of between small pieces of computation.
- Guards: Preserve execution order, gradients, hooks and parameter ownership. Consider fullgraph mode as a diagnostic for unintended breaks within the selected region, and verify compiled execution after warmup. A deliberately partial graph is valid when its total benefit is measured. Check checkpoint keys; in-place module compilation avoids introducing a replacement wrapper.
- Reference: [torch.compile / in-place Module.compile](https://docs.pytorch.org/docs/2.15/generated/torch.compile.html). Check the installed framework version; these APIs are options, not requirements or proof that the intended path executed.

**`repeated_region_compile_reuse`: compile one repeated block and reuse its code**
- Trigger: A deep stack of structurally repeated blocks creates a very large compilation graph and excessive cold-start work. For example, compiling a whole model with dozens of identical transformer layers traces and optimizes each layer's copy separately.
- Technique: Compile the repeated block rather than unrolling the entire stack into one compilation unit. Alternatively, mark a repeated nested region so an outer compilation can reuse its compiled implementation. Parameters remain distinct; the reused object is compiled code, not shared weights.
- Guards: Reuse requires compatible shape, device, stride and behavioral guards. Check state mutation, backward execution and existing checkpointing. Regional compilation leaves surrounding code outside the compiled region, so compare total startup plus runtime. Do not assume one compile serves every block configuration.
- Reference: [Regional compilation recipe](https://docs.pytorch.org/tutorials/recipes/regional_compilation.html), [torch.compiler.nested_compile_region](https://docs.pytorch.org/docs/2.15/generated/torch.compiler.nested_compile_region.html). Check the installed framework version; these APIs are options, not requirements or proof that the intended path executed.

**`opaque_custom_op_boundary`: register an existing kernel as an opaque operator**
- Trigger: An existing custom kernel or unsupported implementation prevents a useful surrounding region from compiling. The compiler tries to trace into code it cannot understand, so it breaks the graph around the call and the surrounding tensor work loses compilation.
- Technique: Keep the same implementation but expose it as a registered opaque operator, for example with `torch.library.custom_op`. Declare its inputs, outputs, mutations and fake execution behavior—a function that computes output shapes and dtypes without running the kernel, registered with `register_fake`—and provide the training backward registration, such as `register_autograd`. The compiler can then retain the call inside a graph without tracing its internals.
- Guards: Mutation and alias declarations must match reality; hidden state or undeclared writes can silently change results. Validate backward and fake/runtime shape agreement. An operator registration does not make a host-synchronizing implementation CUDA-graph-safe. Validate export separately; source-specific lowering adaptations are not a generic public recipe.
- Reference: [Custom-operator registration](https://docs.pytorch.org/docs/2.15/library.html). Check the installed framework version; these APIs are options, not requirements or proof that the intended path executed.
