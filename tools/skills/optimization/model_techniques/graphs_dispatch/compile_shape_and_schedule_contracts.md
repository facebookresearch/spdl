# Compile shape and schedule contracts

These techniques cover dynamic dimensions, bounded shape variants, changing schedule state and data-dependent tensor operations. Open this topic when input or Python-value guards repeatedly fail, or tensor-value branches and data-derived sizes interrupt compilation.

[Model catalog](../index.md) · [Compilation, graph replay and host dispatch](../graphs_dispatch.md)

**`upfront_dynamic_shape_contract`: declare genuinely varying dimensions before first compilation**
- Trigger: Input dimensions genuinely vary, and the compiler repeatedly learns that variation through failed shape guards. By default, compiled code is first specialized to the sizes it observes; when a later input has a different size, the shape guard fails and the code recompiles, possibly several times as different dimensions change. Each recompile stalls training, and repeated recompiles can reach a limit that leaves the region running eagerly.
- Technique: Identify genuinely varying dimensions from actual inputs and recompile reasons, then use the deployed compiler's supported shape contract before initial compilation. The referenced `torch.compile(..., dynamic=True)` is a coarse option, not a precise per-dimension annotation. Keep fixed dimensions specialized where supported and account for independently varying inputs. Find helpers that actually force symbolic sizes to constants rather than assuming every Python conversion does so; preserve supported symbolic shape expressions through the tensor operations.
- Guards: Test the supported size range, including zero/one dimensions and rare combinations. An annotation cannot repair code that forces a size to become constant; locate the actual specialization site. Test unequal dimensions so a coincidental equality does not become a hidden constraint. Retain guards and check runtime as well as startup: dynamic tracing can improve startup yet produce a slower steady-state program, so do not make every dimension dynamic by default.
- Reference: [torch.compile / in-place Module.compile](https://docs.pytorch.org/docs/2.15/generated/torch.compile.html). Check the installed framework version; these APIs are options, not requirements or proof that the intended path executed.

**`bounded_shape_specialization`: map nearby shapes to a few padded buckets**
- Trigger: Many nearby shapes repeatedly incur compilation, graph recording or host-side matrix-kernel selection work. For example, sequence lengths anywhere from 1 to 512 can create hundreds of distinct shapes, each paying its own compile, capture or kernel-selection cost.
- Technique: Map inputs to a small set of shape buckets, such as lengths rounded up to 64, 128, 256 or 512. Pad to the selected bucket, execute its compiled or captured variant, then remove padded outputs. For an already finite shape set, retain separate static variants and warm each supported variant rather than progressively generalizing it.
- Guards: Never silently truncate real examples to fit a bucket. Mask padding from losses, attention and statistics; batch-wide reductions such as normalization statistics can change real outputs despite a masked loss. Preserve sample weighting and ordering. Bound variant memory, provide an overflow path, and price padding and warmup into end-to-end execution.
- Reference: [torch.compile / in-place Module.compile](https://docs.pytorch.org/docs/2.15/generated/torch.compile.html). Check the installed framework version; these APIs are options, not requirements or proof that the intended path executed.

**`tensorized_schedule_state`: pass changing schedule values as tensors**
- Trigger: Changing Python learning-rate or schedule values invalidate compiled training-step guards. A compiled step specializes on a Python `float` learning rate as a constant, so a scheduler that changes it every step forces a recompile at each change.
- Technique: Pass changing numeric state through an operator-supported tensor input instead of a value-specialized Python scalar. Update that state at the original schedule boundary. Select CPU or device storage according to the consuming operator, avoiding a new device-to-host conversion.
- Guards: Confirm the entire consuming API supports tensor state. Do not mutate a tensor that an unfinished backward pass saved; snapshot the value when necessary. Preserve parameter-group schedules, optimizer step counters, serialization and resume behavior. Tensorization alone does not make an optimizer CUDA-graph-capturable.
- Reference: [Compiled optimizer and tensor learning rate](https://docs.pytorch.org/tutorials/recipes/compiling_optimizer_lr_scheduler.html). Check the installed framework version; these APIs are options, not requirements or proof that the intended path executed.

**`tensor_control_flow_and_masked_reductions`: distinguish masked rewrites from data-derived shape support**
- Trigger: compiler diagnostics identify tensor-value branches, boolean compaction or data-derived output sizes in a loss, model or metric block. These are different failures: a fixed-shape masked computation can remove some branches or compaction, while valid variable-sized computation may instead need compiler-supported shape contracts.
- Technique: for suitable compaction or sparse-routing code, data-dependent selection or loops can be replaced with compute-for-all followed by tensor selection or masked weighting. Examples include boolean indexing replaced by input clamping plus `torch.where`, and static expert loops that process all tokens then apply each expert's weight mask. This trades potentially more arithmetic for traceability; it is not, by itself, a recipe for computing means over only the valid elements. Compile-friendly rewrites can speed up training, but a training benefit from masking itself has not been established. Other failures need different mechanisms, such as normalizing a metrics flag to a Python bool or wrapping deque aggregation in a registered custom operator. For data-derived slicing, `torch._check(offset >= 0)` can state the valid offset constraint, but in one tested case compiler fixes for unbacked-symbol handling in copies and broadcast checks were also required. For over-specialization, distinguish dynamic input dimensions from in-graph scalar-derived sizes: use dynamic-shape declarations for the former and `capture_scalar_outputs=True` to retain scalar-derived values as unbacked symbols for the latter. Some data-derived sizes, such as sequence truncation lengths, also need explicit guard handling, for example `guard_or_false`. Do not substitute masking for every dynamic operation.
- Guards: preserve selection, weights, normalization, thresholds, empty-selection behavior and gradients. Static expert loops that send every token through every expert do more work than sparse routing and are slower; benchmark the whole path. Tensor selection does not make unsafe excluded computations safe, so preserve numerical and backward behavior when preparing inputs. Masking examples drawn from inference-oriented fixes may be bundled with other edits (for example an evaluation-mode simplification of random sampling), may remove training or distributed behavior, and may not be semantically equivalent: do not copy such removals into training or treat traceability as quality validation. Converting buffers to Python ints for traceability can also break export. A Python-bool boundary value is not permission to assume arbitrary tensor data is constant. Model-side constraints alone may be insufficient: data-derived slicing and loss compilation can also need compiler-side fixes. Check graph breaks, recompilations, memory and rank coordination on representative inputs: recompilation has been associated with distributed stalls or hangs and with temporary or persistent memory leaks whose cause was not identified. Dynamic-input annotations such as `mark_dynamic` must be applied before tracing and are not a blanket fix for data-dependent guards.
