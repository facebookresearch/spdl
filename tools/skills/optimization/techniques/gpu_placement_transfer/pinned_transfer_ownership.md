# Pinned transfer ownership

These techniques cover physical transfer threads, pinning, device context and cross-stream storage lifetime. Open this topic when transfer delays compute, background copies corrupt inputs or grow memory, registration targets the wrong device, or configured pinning still delivers pageable storage.

[Catalog index](../../technique_catalog.md) · [GPU placement and transfer](../gpu_placement_transfer.md)

**`h2d_cache_depth_and_threads`: bound background transfer ownership and threads**
- Trigger: serial IPC/H2D delays compute, or background transfer introduces NaNs, growing GPU memory or excessive retained batches.
- Technique: reuse a persistent frontend and transfer stream so a background worker can prepare the next device batch while the foreground computes; wait for that batch's transfer before consuming it. Bound both the number of resident batches and the physical threads making transfer calls. A thread-local transfer helper may create a stream and retention cache for each calling thread, so increasing task concurrency through a large executor can multiply both. If the existing consumer omits stream recording on nested tensor leaves, retain all downstream-held storage until completion; a tested retention depth can mitigate that particular path, but explicit stream/event ownership is preferable to guessing a universal batch count.
- Guards: a case went NaN with shallower retention and trained correctly with greater retained depth. Reducing transfer threads cost almost no speed while reducing peak memory. Task concurrency is not physical-thread count: a large physical-thread pool proliferated streams and memory and reached OOM; a dedicated-thread rerun passed the earlier failure window with flat memory, not full-run proof. Reuse threads across rebuilds and close explicitly. Extra overlap is not automatically faster, and transfer completion alone does not cover subsequent consumer-stream use.
- SPDL reference: {py:func}`spdl.io.transfer_tensor_h2d` exposes `num_caches` and uses a thread-local transfer stream. The helper waits for H2D before returning; calling it in the background provides overlap with foreground computation, not an unfinished transfer handed to the caller. Its cache retains recent returned batches, not a preallocated device-buffer pool. Size retained batches from the actual downstream contract; neither a particular cache count nor adding transfer threads is universally safe or faster. See the API's linked CUDA race-condition note for the ownership rationale.

**`record_consumer_stream_lifetime`: retain every transferred storage through device use**
- Trigger: asynchronous transfer or conversion allows storage recycling before a different stream finishes reading it, corrupting inputs.
- Technique: track readiness and storage lifetime separately. Record a producer event after H2D/conversion, make the consumer stream wait for it, and record that consumer stream's use on every device tensor leaf, including labels, identifiers and masks. Alternatively, hold every affected storage until an event recorded after its last consumer operation completes. Capture the caller's stream before arranging background copies, and apply the same contract to conversion temporaries crossing streams. Keep pinned host sources valid until H2D completes; a producer event alone does not protect later device reads from allocator reuse.
- Guards: producer completion is not consumer-storage lifetime; a host reference to the outer batch alone is insufficient for untracked transient storage. Synchronous debug readback masked a demonstrated address-reuse race. Test without such accidental synchronization. Reject faster arms that change data coverage, numerical results or quality.

**`pin_buffers_on_rank_device`: establish device state in the pinning thread**
- Trigger: nonzero-rank background pinning or registration creates unintended GPU-zero contexts and consumes memory on the wrong device.
- Technique: capture the rank's actual device when scheduling buffer registration/transfer, then enter the appropriate device guard inside the physical thread that performs device-runtime calls. Keep that guard around registration and stream/event creation and restore previous thread state afterward. Pinning host memory is not a tensor move to that GPU; the guard prevents implicit runtime initialization on a default device. Skip device-specific setup on CPU-only/unset-device paths.
- Guards: device state is thread-local; setting it in the caller is insufficient. Preserve CPU-only and unset-device fallbacks. Validate physical/visible device identity and account for other external allocations; removing one context leak does not diagnose every memory increase.

**`pin_memory_effectiveness_audit`: inspect the storage actually transferred**
- Trigger: pinning is configured but traces show pageable copies, custom-container bypasses or hidden reconstruction after pinning.
- Technique: inspect actual emitted batch containers and CPU tensor leaves at the final H2D boundary, not only before a pinning stage. Trace whether a custom pinning hook runs and whether its returned object is used; if that hook is intended to own a custom container's traversal, dispatch it before generic mapping recursion. Follow any later clone, concatenation or layout reconstruction and verify that its final storage is still pinned. A pinned input followed by a new pageable allocation loses the intended transfer path.
- Guards: pin CPU leaves only and retain custom metadata and buffer lifetime. Dictionary subclasses can bypass expected hooks; confirm the delivered tensors are actually pinned after all later transforms. Include pinning cost: main-loader pinning alone regressed step time in one comparison, and other pinning comparisons were also slower. Genuine pinning showed no benefit in another tested case where H2D did not limit the consumer; comparing GPU streaming-multiprocessor utilization did not establish a speedup. Fixing pinning does not mean the path is H2D-bound, and results bundled with other changes do not establish a pinning-only benefit.
