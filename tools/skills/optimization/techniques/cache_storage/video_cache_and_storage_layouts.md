# Video cache and storage layouts

This topic covers small-frame caches, clips, subclips, sparse-access encoding and shuffled temporal chunks. Open this topic when retained frames, video seeking or storage layout dominate.

[Catalog index](../../technique_catalog.md) · [Cache and storage](../cache_storage.md)

**`lazy_native_frames_small_detection_cache`: keep small detection images, fetch full frames later**
- Trigger: a video pipeline keeps every decoded full-resolution frame in memory, although detection operates on smaller images and only selected frames need later full-resolution work. The cache pays the full-frame memory cost even for frames that the later consumer never requests.
- Technique: retain the downscaled detection images together with source identity, frame index/timestamp, and the mapping back to each native-resolution frame. Construct those images with the existing resize and color conversion, then run detection on the small cache. Decode or read a full-resolution frame only when a downstream selection needs it, pass it to that consumer, and release it after the work finishes rather than adding every native frame to the detection cache.

  The lazy read must reproduce the selected source frame, not merely the nearest frame returned by a seek. Reduced retained image size can be offset by decoder state or several overlapping full-resolution reads, so include those in the memory budget.
- Guards: preserve selected frames, timestamps, color/layout conventions, and feature outputs. Count temporary buffers, decoder state, and in-flight native frames as well as the small cache. The measured treatment also split stages and included other changes; its time change is not a lazy-read-only estimate.

**`temporal_video_storage_representation`: store nearby frames in video clips**
- Trigger: temporally related video frames are stored as separate image files or raw arrays. Each frame then carries its own storage/request setup, and the representation cannot reuse similarities between nearby frames. A video clip can reduce that repetition, but its compressed layout also changes the work needed to retrieve individual frames.
- Technique: group temporally adjacent frames into clips and build a manifest mapping each sampled frame or window—a requested timestamp interval or consecutive-frame range—to its clip and exact frame index/timestamp. Preserve its annotation association. Choose codec, quality, and keyframe spacing for the actual requests, then open the clip and decode the requested frames or range. Temporal compression can share information between frames and amortize file setup, while a sparse random read may need to decode earlier frames before reaching its target.

  Treat precomputed deterministic resize or other recurring image preparation as a separate representation choice, not an inseparable part of the codec change. Leave stochastic augmentation in training. Compare decoded inputs and downstream outputs against the original representation before accepting lossy encoding.
- Guards: validate compression artifacts, annotations, timestamps, and seeking cost. Temporal compression can hurt sparse random access. Quality checks were limited in one tested case: video-based training initially introduced artifacts, and later preprocessing fixes restored comparable quality only on the tested content. Do not generalize that limited check or attribute a combined preprocessing/codec treatment to the codec alone.

**`video_subclipping`: reuse short clips with aligned video and supervision**
- Trigger: requested timestamp intervals or consecutive-frame ranges are short, but the input path repeatedly opens and seeks through a long original video to obtain them. Reusable subclips can shorten that work only if their starts are decodable and their frames still align with every associated supervision stream.
- Technique: define one time grid for the original video and supervision, align keyframes to the intended boundaries, and create independently decodable chunks. Copying arbitrary compressed byte ranges does not produce an independent clip. Record each chunk's original interval and time origin in its manifest.

  For a chunk starting at original time `t0`, shift retained frame timestamps and every supervision timestamp to `t - t0`. A frame at 12.4 s in a chunk starting at 10 s has chunk-local time 2.4 s, and its supervision must receive the same shift. Preserve the original boundary-inclusion rule and explicitly handle annotations spanning chunks without silently dropping or duplicating targets. If constant-frame-rate normalization is needed for reliable boundaries, regenerate and validate the original-time-to-frame mapping afterward instead of assuming the old frame numbers still apply.
- Guards: fractional frame rates broke exact boundaries in one tested case until constant-frame-rate normalization was added. Check timestamps, frame correspondence, and all supervision streams after normalization. Validate compression/quality effects and count duplicated chunks or bytes as well as decoder savings.

**`episode_locality_with_shuffle`: shuffle video chunks, read nearby frames together**
- Trigger: training samples video frames from many episodes, where an episode is a recorded sequence/video with associated annotations. Uniformly random frame order repeatedly switches videos or seeks to distant frames, disrupting video-reader cache locality. Fully sequential training may be unsuitable, so the goal is to retain shuffle while avoiding a reader switch for every frame.
- Technique: enumerate each episode's valid sampled frames in temporal order and divide them into deterministic consecutive-frame chunks. The chunk size specifies how many consecutive entries from that valid frame sequence are read together; preserve the existing policy for the final partial chunk. Represent each chunk by episode identity and its ordered frame indices or range. At each epoch, reproducibly shuffle the global chunk list, partition it deterministically across ranks, and emit frames in order within each assigned chunk. Nearby reads can reuse video reader/decoder state while the order of chunks changes between epochs.

  Preserve per-frame augmentations and the sample universe. Save both chunk position and position within the chunk for resume. Compare consecutive-frame chunk sizes with the same batch/tail policy: larger chunks change the temporal correlations and batch composition seen by training, not merely decode efficiency.
- Guards: check distributed coverage, diversity, batch composition, and deterministic resume. Promote only after quality checks on the changed sample-order correlations. Count decoder/cache memory as chunk size grows. The mechanism here is video-reader locality, not a general claim about every sequential input source.

**`intra_frame_storage_random_access`: reduce video frames decoded before a sparse target**
- Trigger: sparse random video requests ask for isolated frames from a temporally compressed stream, such as H.264. Some pictures store their own image information; others depend on pictures decoded earlier. Reaching a target can therefore require starting at an earlier safe random-access boundary and decoding many frames the consumer never uses. A generic keyframe/I-frame flag does not guarantee that following frames are independent of everything before that boundary.
- Technique: profile requested frame positions and the preceding decode work. Compare an all-intra layout, where every frame is encoded independently, or shorter intervals between suitable random-access boundaries. For the latter, use boundaries whose following group of pictures does not depend on earlier pictures—for example appropriate H.264 IDR or closed-GOP boundaries—not merely more frequent frames labelled as keyframes. Keep the stream/container metadata needed to initialize decoding. These layouts can start decoding closer to the target, but generally give up some temporal compression. Update the manifest while preserving requested frame/timestamp and annotation mappings, then verify the same sparse requests and decoder outputs against the original clip.

  Choose using decode work, encoded size, encoding cost, and expected access frequency/reuse. There is no universally best codec or keyframe interval, and a size tradeoff measured on one clip need not hold for other content or access patterns.
- Guards: measure storage and encoding costs as well as decode savings. Validate pixels or acceptable compression quality, timestamps, and annotation equivalence. A sparse-access improvement can lose to temporal compression during sequential traversal.
