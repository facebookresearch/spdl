# Host CPU and memory isolation

Open this topic when co-located input work delays the trainer's CPU threads or when the same work costs more cycles per batch because of memory-bandwidth or topology contention, rather than because of pool sizing.

[Catalog index](../../technique_catalog.md) · [Process runtime environment](../process_runtime.md)

**`protect_trainer_cpu_scheduling`: keep co-located input work from starving trainer threads**
- Trigger: loader, decode or transform workers on the trainer host compete with CPU threads that schedule GPU work, leaving those threads waiting while the GPU idles. Oversized, mostly idle pools, such as compiler workers, are a sizing problem: right-size them (see `cap_native_thread_pools`) rather than expecting scheduling isolation to fix them. Small, fast models can separately exceed the host's CPU/DRAM processing capacity; distinguish that capacity limit from scheduling interference rather than assuming more input workers cause the same defect.
- Technique: use host-level scheduling isolation, such as a suitable custom CPU scheduler loaded as a BPF program through upstream Linux `sched_ext`, to reduce interference between trainers and co-located CPU processes. `sched_ext` provides the framework, not a turnkey policy with guaranteed training benefits: select or implement a policy for your workloads and validate it rather than assuming any off-the-shelf policy gives the same results. It is not an input-loader setting. Enable it gradually and per job attempt, so a scheduler failure falls back to the ordinary scheduler on the next attempt instead of crash-looping, and monitor kernel lockups and abnormal scheduler exits. Compare like-for-like workloads, exclude application-failure effects, and group workloads with comparable model and resource behavior. If using a proxy metric, confirm that it tracks real application throughput under both the ordinary and custom schedulers. Use an idle-resistant throughput aggregation, such as a high percentile or time-bucket aggregation, alongside an A/A baseline of unchanged runs; where possible, toggle the scheduler within one run. CPU affinity, cpuset separation, niceness and scheduling priority are untested alternatives here, not validated replacements for the custom scheduler. If tried, validate them the same way. Size thread pools separately (see `cap_native_thread_pools`).
- Guards: validation on hosts that run one training job does not establish behavior on hosts shared by several jobs; validate those separately. A policy that caps preprocessing CPU can regress preprocessing latency through interrupt (IRQ) pressure; correct the policy rather than accept the regression. Measure worker latency/throughput alongside trainer throughput. An aggregate gain does not mean every workload improves: some jobs may show no gain or regress, and unchanged-run comparisons can show substantial variance. Check cross-socket latency and kernel compatibility before adoption; some platforms need a kernel update first, and scheduler changes carry kernel reliability risk. When the scheduler ships together with other input-pipeline changes, its own effect cannot be separated from theirs. Policy co-tuning may remain necessary as preprocessing thread counts scale; reducing that burden through automatic tuning is a goal, not an established capability. Behavior when input workers consume most host CPU remains unvalidated. Host memory bandwidth can be the primary preprocessing-thread scaling limit; scheduling isolation does not remove it. Trainer NUMA pinning is a separate change.

**`memory_bandwidth_topology_isolation`: avoid memory-bandwidth contention on the host**
- Trigger: the same input and code cost more CPU cycles per batch, without network or throttling explanations.
- Technique: map loader CPU affinity to memory-controller/chiplet topology and compare a packed placement with a spread placement, using identical input work and worker counts. Coordinate first-touch memory placement so spreading cores does not merely add remote-memory traffic. Separately avoid or isolate memory-bandwidth-heavy co-tenants. These interventions seek more available bandwidth, not more worker concurrency; check per-batch cycles and bandwidth alongside throughput.
- Guards: the placement remedy itself was not validated. Light sessions were largely unaffected.
