# Garbage collection

[Catalog index](../../technique_catalog.md) · [Process runtime environment](../process_runtime.md)

These techniques implement an application-owned policy for cyclic garbage collection (GC), which reclaims unreachable reference cycles that ordinary reference counting cannot release. Follow the [GC policy](../../gc_optimization.md) after migration parity: retain validated lifecycle hygiene even without an isolated speed gain, preserve the untouched original baseline, and repair or document an exception for an unsafe or regressing policy. Additional collection pauses still need separate justification; hygiene is not a claim of faster training.

**`epoch_cycle_collection`: collect reference cycles at quiescent loop points**
- Trigger: GPU memory grows across epochs on the slowest ranks, and a `gc.DEBUG_SAVEALL` capture shows CUDA tensors held by cycles through exception tracebacks or iterator frames; or native-inclusive profiles show collection stalls in batch production.
- Technique: break the diagnosed cycle at its source or run one `gc.collect()` at a supported quiescent epoch start, after prior consumers have released their references. A cycle can keep a batch reachable through its own traceback or iterator even after the trainer stops using it; cyclic collection can reclaim it only when no live owner remains. Where automatic collection stalls production, use the application's supported policy to suppress it in hot paths and collect at a fixed completed-step or epoch boundary across ranks. Equal step intervals do not guarantee simultaneous pauses; compare actual collection events instead of adding an unmeasured barrier. Keep this within the GC policy in the bundled `gc_optimization.md`, including exception/cancellation cleanup and restoration of prior automatic-GC state. Keep `gc.DEBUG_SAVEALL` diagnostic-only: it deliberately retains unreachable objects, so restore previous debug flags and release captured diagnostic references after inspection.
- Guards: do not blanket-disable GC; prove that cyclic and retained memory stay bounded. Too-frequent manual collection hurt, and tuning the interval alone did not generalize. Periodic forced GC without a recurring steady-state GC tail did not help ([negative_results.md](../negative_results.md)). Attribute the actual holder, not a waiting thread. Correctness-required collection and cleanup remain necessary even when an extra cadence has no speed benefit.
- SPDL reference: Follow the [GC policy](../../gc_optimization.md) rather than adding collection to every pipeline. SPDL iterator shutdown does not prove downstream tensor/traceback cycles are gone; the original cycle diagnosis and a measured quiescent collection point remain necessary.

**`freeze_long_lived_python_objects`: freeze the stable heap before training**
- Trigger: collections repeatedly scan persistent training objects, or forked workers repeatedly collect inherited objects.
- Technique: under the application's existing process-wide GC ownership, build stable training/configuration objects, remove temporary references, call `gc.collect()` and then `gc.freeze()` before entering the loop. Freezing moves currently tracked objects out of future cyclic-GC scans while ordinary reference counting continues; it does not make objects immutable or disable automatic collection of newly tracked objects. Do not freeze transient batches or tensor/traceback cycles. When the owner policy finishes or refreshes that heap at a quiescent boundary, `gc.unfreeze()` returns the objects to the oldest generation; it does not collect them, so run collection where safe under that policy. If an otherwise safe worker layout uses fork, freeze before that fork to reduce inherited-heap scanning; this is not permission to fork a CUDA-initialized trainer.
- Guards: frozen cycles remain outside cyclic collection until unfrozen, so check long-lived cycles and memory growth, including tensors or resource leases linked into the frozen heap later. Freeze/unfreeze affect the whole process: do not unfreeze another component's heap or claim exact restoration of a pre-existing frozen set. Follow the GC guide's normal-end, exception/cancellation and prior-state cleanup contract; explicit close/release remains required. Longer collection intervals alone did not generalize.

**`memory_gated_cycle_collection`: collect explicitly only under memory pressure**
- Trigger: explicit collections run often although host memory is ample.
- Technique: at existing explicit-collection checkpoints, read memory usage against the applicable host/container limit and skip collection while usage is below a chosen threshold, usually with `freeze_long_lived_python_objects`. Use a consistent numerator and denominator, not host-wide free memory for a container-limited process. The gate avoids unnecessary scans; collection can reclaim unreachable cycles, not live caches or merely allocator-retained pages. Keep a separate bounded-growth check so repeated ineffective collections do not hide a leak. Gate optional pressure-driven scans, not correctness-required lifecycle collections, resource release or exception/shutdown cleanup in the application's GC policy.
- Guards: average host memory rose. A job with growing memory repeatedly crosses the threshold and collects every time. After freezing, step-interval tuning added nothing.

**`timeout_sentinel_not_exception`: return a sentinel for cross-thread timeouts**
- Trigger: repeated timed-out reads accompany growing GPU memory.
- Technique: make a timed-out cross-thread read return a distinguished value, such as a private singleton compared by identity, instead of storing or transporting a traceback-bearing exception. The caller can retry or raise a fresh timeout exception without retaining the producer's frames and batches. Keep the sentinel distinct from valid data, exhaustion and non-timeout errors, and separately finish or cancel the outstanding read so a late result does not remain retained.
- Guards: preserve timeout semantics for the caller. Other bounded memory steps were not explained.
