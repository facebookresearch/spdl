# Memory and allocators

[Catalog index](../../technique_catalog.md) · [Process runtime environment](../process_runtime.md)

**`allocator_retain_freed_pages`: stop page-fault churn in workers**
- Trigger: worker processes repeatedly allocate and free large buffers per batch; profiles show high kernel/page-fault time.
- Technique: retain freed pages inside the existing allocator so the next batch can reuse them instead of faulting them back in after the allocator returned them to the operating system. Where supported, lengthen dirty/muzzy decay (the delay before jemalloc purges freed pages) for the trainer and workers. Apply configuration before allocator initialization and confirm that the process actually uses that allocator; this is not an SPDL allocator setting.
- Guards: retaining pages can substantially increase anonymous memory, so check headroom under the container limit across all workers and ranks. On kernels where lazy purge crashes native code, `immediate_purge_avoids_madv_free_loss` requires eager purge instead; do not apply retention on that affected path without a validated safe allocator policy.

**`immediate_purge_avoids_madv_free_loss`: purge eagerly on kernels with `MADV_FREE` failures**
- Trigger: a native loader library segfaults under memory pressure during lazy page purge, destroying caches and stalling input.
- Technique: identify the allocator used by the failing library and configure it to purge muzzy pages immediately via `MADV_DONTNEED` instead of the affected `MADV_FREE` path. Muzzy pages are freed pages awaiting reclamation after lazy purge; eager discard avoids that lazy-reclamation path. Apply the policy before allocator initialization, then trace actual purge syscalls under the same memory pressure: an option named "immediate" is insufficient if the linked allocator still issues the problematic calls.
- Guards: kernel- and allocator-specific. Propagate the setting through the library's own (possibly prefixed) allocator configuration, preserving inherited settings. Purging costs some CPU.

**`bound_allocator_arena_count`: cap allocator arena fan-out**
- Trigger: host memory grows with worker count, and allocator arenas multiply across processes and threads.
- Technique: reduce the arena-count limit of the allocator actually linked into each loader/client process before constructing its pools. Arenas are separate allocation domains that can each retain free chunks; many lightly used arenas multiply retained memory. Compare whole-host resident/anonymous memory and allocation contention with identical worker counts, rather than treating the cap as a limit on total allocated bytes.
- Guards: use the configuration namespace of the allocator actually linked. Weigh fragmentation against contention, and account for the whole host.

**`zswap_aware_loader_memory_budget`: use compressed-swap headroom in producer admission**
- Trigger: memory-bound producer work is limited by a memory-based concurrency controller on hosts where compressed swap is already enabled and supplies additional headroom. Workloads limited elsewhere may see little benefit.
- Technique: make the controller's admission policy swap-aware rather than treating resident RAM as the only usable capacity. This can admit more concurrent producer work; it changes concurrency admission, not tensor size. Compressed swap first stores compressed pages in RAM and can spill to disk when that pool is exhausted or compression fails. Compare swap-aware and swap-unaware admission with swap and scale-down policies otherwise held constant. Raising a swap-utilization target when more swap is available is proposed further tuning, not a universally safe setting or a separately measured benefit.
- Guards: available swap varies by host and can be shared among containers; a fixed target does not transfer automatically, and batch success can remain host-dependent without a per-batch memory contract. In one comparison, OOM frequency increased on some host types after more aggressive settings, while remaining below the no-swap baseline; the increase was observed, but its cause was not isolated. Monitor CPU, resident-plus-swapped memory and network use: they can rise faster than useful throughput as the host approaches saturation. Do not generalize dedicated-producer results to producers sharing a host with trainers; swap there can cause excessive trainer memory use, and shared-host combinations remain unvalidated. Scaling down producers can discard work. Data-loss outcomes were not established, and suspected increased data starvation was not measured; either could offset efficiency gains. Measure coverage, reliability and trainer starvation, not producer throughput alone. Full output queues and idle producers do not prove lower aggregate resource demand; higher per-host throughput reduces resource use only when surplus allocations actually shrink. In one controlled comparison, more work was processed with fewer producers, but the broader effect of that additional work remained unresolved. Results under plentiful producer capacity do not establish results under capacity pressure. Measure disk writes from swap spill against SSD endurance; in one tested case writes were low enough to mitigate that concern, not an observed endurance regression.
