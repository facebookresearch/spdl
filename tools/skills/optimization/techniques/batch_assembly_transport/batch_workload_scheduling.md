# Batch workload scheduling

This topic covers background assembly, length and cost balancing, budgeted packs and shape buckets. Open this topic when batch variability, rank skew or shape proliferation stalls training.

[Catalog index](../../technique_catalog.md) · [Batch assembly and transport](../batch_assembly_transport.md)

**`buffered_length_bucketing`: balance iterable batches without retaining outliers**
- Trigger: variable-length iterable inputs produce large rank-to-rank preprocessing differences and collective waiting without a global sortable index.
- Technique: keep a bounded local sample buffer, sort its current contents by length, select a batch at spaced positions across that range, remove the selected samples and refill. A strided selection mixes short and long work within a batch rather than always taking only the shortest items; similar work totals can reduce rank skew. Choose and rotate the selection so long outliers are eventually consumed rather than retained indefinitely. For illustration, selecting lengths `[4, 8, 12]` from `[2, 4, 6, 8, 10, 12]` reaches the long end; the retained `[2, 6, 10]` must also be consumed. This illustrates coverage, not a prescribed stride or a validated scheduling algorithm.
- Guards: naive selection from the beginning of the buffer accumulated the longest samples and slowed prolonged training. The corrected case began selection at the stride instead; this is evidence for that implementation, not a universal indexing rule. Validate long-run row conservation, coverage, fairness, length distribution, seeds, resume state, loss and time spent waiting at the slowest rank—not only an early fast batch.

**`background_shape_grouped_rebatching`: assemble compatible batches ahead of compute**
- Trigger: the trainer's foreground thread waits while it groups incoming samples or input chunks by compatible shape, assembles a complete batch, or receives its payload through IPC. These pauses leave no model work queued even when input preparation could run ahead.
- Technique: move the same shape grouping and assembly into a trainer-side background stage. Accumulate incoming items until the original grouping rule yields a complete batch, then publish that batch into a bounded ready queue for the foreground trainer. Preserve the original mapping from input chunks to samples and training batches. This overlaps preparation with compute and moves its pauses off the foreground thread; it does not make grouping or IPC free.
- Guards: preserve grouping and batch semantics. Provide queue timeouts, an end-of-data sentinel, exception propagation, stop events and synchronized shared state. Flush partial groups deterministically. Prefetch cannot repair sustained underproduction, and queued storage must remain valid until consumed.

**`workload_weighted_rebatching`: balance fixed-size batches by estimated work**
- Trigger: batches with the same sample count have very different processing cost because histories, sequences or media sizes vary, causing rank skew or memory peaks.
- Technique: when reordering is permitted, keep a bounded window of samples or existing input chunks, estimate their consumer work, and regroup heavy and light items into batches with comparable total cost while retaining the required sample count. For illustration, costs `[1, 2, 8, 9]` can form two-item batches `[1, 9]` and `[2, 8]` instead of a cheap and an expensive batch. This is a balancing example, not a prescribed sorting algorithm. Use a cost model that matches the representation: summed lengths for concatenated sequences differ from maximum length times count for padded sequences. Unlike `token_budget_balanced_packs`, this need not change batch cardinality.
- Guards: do not regroup when exact batch membership or order is part of the task contract. Preserve paired samples, labels, example/gradient weights, global batch size and long-run coverage; account for batch-dependent operations and validate quality. Drain all buffered items exactly once and checkpoint window/order state for resume. Prevent repeated selection of cheap samples from retaining heavy items indefinitely. Include the estimator, buffering and assembly cost; balanced predicted work is not proof of faster completed training.

**`token_budget_balanced_packs`: bound useful work rather than sample count**
- Trigger: fixed sample counts create unequal token, frame or pixel work across ranks.
- Technique: accumulate samples while the proposed pack's cost remains within a token/frame budget, emit the pack before the next sample would exceed it, and start a new one with that sample. Define cost from the consumer's actual work: a sum of lengths for concatenated tokens differs from maximum clip length × clip count for padded clips. Preserve an existing frame-budget rule rather than accidentally switching cost models; for mixed-aspect media, normalize pixel area before packing. Variable sample counts can make work more even across ranks, but the budget is a workload-specific proxy, not a guarantee of equal latency.
- Guards: emit oversized samples alone, allow an appropriately relaxed minimum and flush on exhaustion so examples cannot be trapped indefinitely. Preserve global-batch and gradient weighting, sample conservation, randomization and checkpoint state. Higher utilization does not justify different training semantics without quality validation.

**`per_step_global_length_election`: align the length class of synchronized batches**
- Trigger: independently chosen video lengths make nearly every distributed step wait for the longest-rank work.
- Technique: maintain local prefetched pools indexed by length class and elect one shared target class for each synchronized step. Confirm that every rank can supply that class before consuming its next batch; replenish or rebalance depleted pools under the existing sampling policy rather than letting a rank silently choose another class. Matching classes reduces length-driven work skew, while the readiness check addresses the case where agreement alone leaves a rank with no matching input. Keep this coordination within the existing synchronized training topology.
- Guards: account for the per-step collective, capacity needed for every length and deterministic exhaustion handling. Preserve length distribution, sample coverage, ordering constraints and resume state; insufficient pools can reintroduce desynchronization. In one comparison, a shared length choice alone still left rank skew; check actual readiness and input balancing too.

**`round_packed_length_to_bucket`: limit input shape proliferation**
- Trigger: varying packed lengths cause expensive compiler warmup or too many runtime shapes in a baseline already sensitive to shape specialization.
- Technique: after forming a pack, pad its length `L` to `((L + Q - 1) // Q) * Q` for a fixed positive quantum `Q`, keeping the added positions masked. For example, `L=513, Q=256` produces length `768`. Reusing a smaller set of shapes can reduce specialization and warmup work, at the cost of executing some padding; select the quantum by that tradeoff rather than minimizing shape count alone.
- Guards: measure useful-token throughput and preserve masks and sequence boundaries. Packing across convolutional boundaries can be invalid. Almost-unpadded batches may not benefit from packing; do not infer a model-execution win from fewer shapes alone. Lower compile warmup did not guarantee faster steady steps; a packed path was slower than the existing padded attention path.
