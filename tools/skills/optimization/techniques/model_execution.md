# Model execution adjacent to the input path

These entries sit where data delivery meets model execution: the training step consumes loader output, so a slow step can come from either side. Each one changes what the model step computes or how it computes it, not just how data is loaded. Treat them as model hypotheses that can be tested alongside input work rather than after every input idea is exhausted. The [cached model benchmark](../cached_model_benchmark.md) times a change on real GPU-ready batches with distributed communication intact; that isolates model work but is not end-to-end cost or quality evidence. Attribute a production speedup only from measurements on the real path. Keep the effective batch and distributed topology fixed, and use the original model for quality comparisons.

**`device_resident_matching`: remove per-sample host round trips in the loss**
- Trigger: a loss matches predictions to targets one sample at a time. For example, a Hungarian-style matcher builds a cost matrix on the GPU, copies it to the host with `.cpu()`, and runs a CPU assignment solver such as `scipy.optimize.linear_sum_assignment` for each sample. Each device-to-host copy waits for the GPU work needed to produce and copy that tensor, not necessarily unrelated work on other streams or devices; the host then launches that sample's many small gather and reduction kernels. With many samples per batch, the GPU idles between short bursts even when input batches are ready.
- Technique: keep the whole matching loss on the device. Build the batch's cost matrices together, solve them with a batched device solver, and perform the resulting gathers and reductions as batched tensor operations. Because samples have different numbers of targets, prepare the required dense metadata during collation, such as targets padded to a per-batch maximum plus valid-count or mask tensors, so the step does not rebuild per-sample Python lists. The matching objective stays the same; only where and how it is solved changes.
- Guards: equal-cost ties can produce different valid assignments. Compare objective values, losses and gradients rather than requiring identical tie choices. Preserve masks, empty cases such as a sample with no targets, and the original matching objective; padded entries must never be matchable. Count any additional device memory and remaining synchronization.

**`reduced_precision_compute`: evaluate lower-precision compute without changing optimizer state**
- Trigger: a small high-throughput model spends substantial training-step time in floating-point compute that may tolerate reduced precision, as shown by a profile of the real path or a cached native benchmark.
- Technique: BF16 keeps FP32's exponent range, so it rarely overflows where FP32 does not, but stores 7 explicit fraction bits instead of 23, so it rounds each value more coarsely. Compare compatible BF16 model operations, for example under `torch.autocast` or explicit casts of selected modules, against the FP32 baseline. Retain FP32 master parameters and optimizer state where the training recipe requires them. Convert only supported operations and keep loss-sensitive reductions in their original precision; do not cast the entire training state blindly. Candidates include packed BF16 computation in eager execution and BF16 feature computation.
- Guards: this is a model-specific experiment, not an input fix or an SPDL loader utility. Hold data, effective batch, optimizer and distributed topology fixed. Verify numerical stability, outputs, losses and gradients, then require non-degrading final model quality against the original baseline; do not infer acceptable quality from throughput or from reduced storage precision. Speed depends on hardware, operator shapes and conversion overhead.

**`norm_layout_materialization`: avoid redundant layouts and materialize only where needed**
- Trigger: the step repeatedly converts tensor layouts around normalization, for example with `.contiguous()` or a `permute` followed by a copy, or passes strided (non-contiguous) operands that make native kernels select slower generic execution paths. Each conversion reads and writes the whole tensor, and a slow path can cost more than the arithmetic.
- Technique: remove conversions around FP32 normalization that do not change the result, such as a copy whose layout a later operation immediately changes back. Where a consumer genuinely benefits from contiguous data, materialize its required layout once, reuse it for every consumer that needs it, and include that copy in the timing.
- Guards: preserve arithmetic order and test parity on the actual library build and thread configuration. Do not fuse changed mathematics into a layout experiment. A faster contiguous consumer is not a win if its materialization or increased memory outweighs it.

**`fused_copy_widen`: fuse strided materialization and dtype widening**
- Trigger: model execution first materializes non-contiguous BF16 device activations and then widens them to contiguous FP32 before a normalization operation, paying separate copy/conversion work.
- Technique: for an eligible physical layout, replace those two passes with one conversion-capable device copy kernel that writes a fresh contiguous FP32 result. One opt-in implementation uses a masked tiled Triton kernel that widens BF16 by appending zero bits while materializing the strided input. It keeps the native FP32 layer-normalization forward/backward with the same normalized shape, weights, bias and epsilon, and a custom autograd backward converts the returned input gradient to BF16 using the native cast. This targets an intermediate allocation and memory pass, not normalization arithmetic.
- Guards: keep the fused path opt-in behind explicit prerequisites and eligibility checks: use it only when the model already runs its forward in BF16 with the matching normalization layout, and route scripting, tracing, CPU, evaluation and unsupported layouts to the original path. Preserve fresh-output ownership and backward/VJP semantics, not only ordinary forward values; test NaN payloads, subnormals, signed zero, tails, storage offsets and gradient strides against repeatable native controls. Treat it as experimental and default-off: in one tested case it gave only a small isolated reduction in cached native model-plus-collective latency, which is not proof of neutrality, end-to-end training speed, cost, accuracy or bit parity. In that case the CUDA correctness tests and CUDA-only cases had not been run on GPU for the exact implementation, and training speed and accuracy were not measured. Run those GPU correctness checks and measure end-to-end training and quality; do not promote fusion on latency alone.

**`selective_kernel_replacement`: replace only a measured input-adjacent hot primitive**
- Trigger: on a training path that already receives batches, one operator at a specific shape or stride remains disproportionately slow, or a CPU postprocessing operator competes with input preparation for the same cores.
- Technique: substitute a validated native implementation only for the consumed hot primitive and its supported shapes or strides; keep the original implementation for every other case, so unsupported inputs do not silently change behavior.
- Guards: establish the actual bottleneck; core contention can be suspected without being proved, as in one case. Validate pixels, labels, dtype, RNG, fused arithmetic and trained quality: in one tested case an image-library substitution made epochs faster but changed pixels, so timing alone cannot justify it.
