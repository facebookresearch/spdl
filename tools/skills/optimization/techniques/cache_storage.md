# Cache and storage

These techniques reduce the bytes an input pipeline reads, the work it repeats, or the resources it keeps while preparing training data. A cache stores something already fetched or computed so a later request can reuse it. That something might be a downloaded file, a decoded record, metadata, or a live video reader; each has a different cost and lifetime. Measure first-time reads and repeated cache hits separately, including the cost of filling and retaining the cache.

Here, a **row** or **record** is one logical set of related values, such as a path, a label, and feature tensors. In a table, records are rows and the named values are **columns** or **fields**. A stored record is not necessarily one training sample: several records may form a sample, and one record may expand into several examples. Likewise, a cache entry may contain one record, a chunk, or a batch. Preserve these mappings when changing storage or batching.

**`direct_io_cache_reads`: avoid retaining local cache bytes in RAM**
- Trigger: an input cache holds large records on local disk, but reading or writing them also fills the operating system's page cache—the RAM used to retain file contents. That extra copy competes with the trainer and loader's own memory. Look for page-cache growth near the container limit, increasing reclaim or swap, slower successive epochs, or memory-pressure kills. A file being cached on disk does not mean its bytes should also stay in RAM.
- Technique: read local cache hits with `O_DIRECT`, which bypasses the page cache, into page-aligned buffers owned by the reader threads. Because this removes buffered readahead—the kernel reading nearby bytes before they are requested—overlap the cache-hit reads requested by a batched dataset/cache lookup through a bounded reader pool rather than reading every record serially.

  Treat cache-miss writes as part of the same policy. Write a temporary file, synchronize its contents with `fdatasync`, advise the kernel to discard its buffered pages with `POSIX_FADV_DONTNEED`, close it, and rename it into place. Otherwise, newly fetched records can still fill the page cache even though later hits use direct reads.
- Guards: the filesystem may reject direct I/O or require particular buffer, offset, and length alignment; handle those cases explicitly. Bound reader buffers and concurrency. Direct reads with buffered miss writes were slower in one case, as were serial direct reads. Per-file `POSIX_FADV_DONTNEED` after buffered reads blocked reader threads in the kernel on some hosts, so do not assume that advisory eviction is an equivalent cheap substitute. A failed write must remove its temporary file and leave the record eligible for refetch, not lose a sample.

**`raw_cache_format`: avoid unnecessary serialization and reader copies**
- Trigger: an input cache repeatedly writes and reads tensor or record payloads using general-purpose serializers. Profiles may show time in `torch.save`/`torch.load`, pickle or archive parsing, generic tensor serialization, or handling many small files. Also screen for `numpy.load`, especially `numpy.load(io.BytesIO(data))` when numeric NPY bytes are already in memory. These API names are cues to investigate, not proof that changing them will improve training.
- Technique: separate the cost of the stored format from the cost of its reader. `torch.save`/`torch.load` use pickle for object metadata and store tensor storages separately; they do not simply pickle all tensor bytes. If that generality is expensive for the input-cache fields actually retained, compare a specialized container with a magic number (a fixed marker identifying its format), a compact name/dtype/shape/offset/length header, and 64-byte-aligned tensor bytes. If only an outer archive is unnecessary, keep the inner payload and replace that wrapper with a suitable representation such as NPY.

  An existing NPY cache need not change format just to avoid a reader copy. For ordinary numeric NPY arrays, NumPy's file-like reader allocates an output array and copies values from the read chunks into it, including when the input is `io.BytesIO` over bytes already in memory. For supported in-memory NPY payloads, compare `spdl.io.load_npy(data, copy=False)` against that reader. This is not a claim that every `numpy.load` path copies: file-backed memory mapping differs, object arrays use pickle, and NPZ archives are a different case. For many small records, another option is to publish bounded, indexed shards atomically and map them locally, reducing per-file and small-remote-read overhead. Detect old and new formats during rollout and treat corrupt cache entries as misses. This technique concerns input caches, not blanket replacement of model or optimizer checkpoints.
- Guards: validate header fields, dtypes, shapes, offsets, lengths, and region bounds before exposing data. Preserve shape and Fortran layout for NPY, reject malformed metadata, and check whether consumers need writable or independent storage. `spdl.io.load_npy` does not support object, structured, or record dtypes. Every returned view must retain its backing buffer. Preserve the inner payload and cache identity unless changing them is a separate hypothesis; verify shard ordering, shapes, and complete publication. A format swap alone showed warm-read parity within reported statistical uncertainty in another case, so lower parsing complexity is not a speed guarantee.
- SPDL reference: for an NPY payload, {py:func}`spdl.io.load_npy` with `copy=False` returns a zero-copy array that retains the source buffer and inherits its read-only or writable state. Request `copy=True` for independent writable storage. This is not a serializer or a reader for arbitrary raw or safetensors formats.

**`zero_copy_decompress`: decompress into the buffer the consumer will use**
- Trigger: a cached record contains compressed array data. The loader decompresses it, converts the result to a new `bytes` object, and then copies those bytes again while building NumPy arrays or tensors. Profiles show decompression/deserialization CPU, memory copies, or page faults rather than remote-read latency. The repeated copies are wasteful when the decoded fields could safely refer to the decompression output.
- Technique: allocate one output buffer of a validated size and decompress directly into it, using a decoder's `readinto` operation when available. Parse each needed field's dtype, shape, and byte range, then return a NumPy or tensor view over that range instead of allocating another copy. For a field at byte offset `o` with length `n`, `memoryview(buffer)[o:o + n]` illustrates the selected range; the returned array or tensor must retain the buffer owner. Make an aligned copy only for a consumer that cannot safely use the original range.
- Guards: bound the declared decompressed size before allocation. Validate field bounds and agreement between dtype, shape, and byte length before exposing views. Retain the owner for every view, and check bit identity for every accepted input type, including bytes, memoryviews, and tensors. Unsupported formats must use the original decoder; inconsistent headers must follow the original fallback or corruption-error contract. The range example explains ownership, not a complete format parser.

**`slim_stored_rows`: stop transporting fields that are never consumed**
- Trigger: first-time acquisition or a capacity-limited cache spends most of its time or space on bytes per record. The stored records include fields that training does not read, but those fields still travel through storage, transport, and deserialization. Keeping fewer records cold can help only if the retained representation still supplies everything the consumer needs.
- Technique: list the fields used by training and evaluation, including fields needed to derive other values. Repack records with that complete required set, or use column projection before reading, transporting, or deserializing when the storage path supports it. For example, if only path and label are needed and an unrelated stored payload has no downstream dependency, avoid fetching that payload. Keep the original record-to-sample mapping and row order when sampling by position.

  Narrower numeric storage is a separate precision hypothesis: a value can be stored in a smaller dtype and widened after decoding, but widening does not recover information lost during storage. Evaluate that change separately from removing unused fields.
- Guards: compare repacked records by key and content hash, and verify order when reads are combined. Preserve required- and optional-field behavior in both training and evaluation. Analyze precision loss and overflow before narrowing; dropping a consumed feature requires quality validation. Check retention and expiry of the repacked copy. A smaller index can worsen lookup-tail latency, so fewer bytes alone do not establish a faster input path.

**`cache_capacity_all_disks`: spread cache entries across dedicated local disks**
- Trigger: the local cache repeatedly evicts part of the dataset, leaving a fixed fraction cold each epoch, while other dedicated cache disks are unused. The problem is usable capacity rather than necessarily read bandwidth: every miss must acquire the evicted data again.
- Technique: choose one stable list of eligible local disk mounts and map each cache key deterministically to a disk, for example with a stable digest modulo the number of mounts. Use exactly the same mapping for reads and writes. This turns several dedicated disks into aggregate cache capacity instead of placing every record on one disk. Exclude shared devices, temporary devices, and directories that merely exist without the intended filesystem being mounted.
- Guards: keep the mount list and key mapping stable across epochs, or explicitly invalidate and rebuild the cache when they change. Budget free space on each device, including concurrent writers, and handle device loss or write failure as a miss/refetch rather than lost data. More capacity does not demonstrate more read bandwidth or faster training; measure which misses it actually removes.

**`lookup_rows_per_call`: combine cache-aware batched lookup requests**
- Trigger: one training batch requires several sequential dataset/cache lookup requests. Each request accepts multiple record keys, serves hits locally, fetches misses remotely, and returns only after its slowest miss completes. Even with a high hit rate, a few misses can make the loader wait at several separate request boundaries.
- Technique: combine those small lookup requests into fewer larger requests when the client already fetches misses within a request concurrently. Four sequential lookups of 64 records each wait for four separate slowest misses; one lookup of the same 256 records can overlap the misses and wait at that boundary once. This changes request grouping, not the requested records, and it does not create overlap in a client that fetches keys serially. After the combined result arrives, reconstruct the original order, duplicates, and batch structure.
- Guards: bound cold-cache requests and the memory retained while waiting. A whole-batch request with many workers reached the container limit, and another request-batching test reported errors at the tested sizes. Respect service concurrency and rate limits and monitor throttling. Preserve duplicate and empty-record positions, ordering, and partial-result/error behavior. A larger request is not automatically a safe or faster request.

**`lookup_concurrency_from_latency`: overlap enough remote requests to feed training**
- Trigger: a remote lookup spends much of its elapsed time waiting for a response, leaving CPU or GPU idle between requests. When the service is not already saturated, approximate read throughput is concurrent requests × records per request ÷ request latency. One request at a time may therefore deliver fewer records per second than the trainer consumes, even though each request is reasonably fast.
- Technique: estimate a starting in-flight request count with `ceil(trainer_rows_per_second * request_latency_seconds / rows_per_request)`. Demand of 1,000 rows/s, latency of 0.2 s, and 50 rows per request suggests about four overlapping requests before allowing for variability. Measure completed throughput and latency tails, then adjust the lookup stage within its service and memory budgets. A native asynchronous client can overlap waiting without allocating a thread for each request; a synchronous client needs a separately measured executor-thread budget.
- Guards: count requests across all ranks and workers, not just one stage instance. Check client thread safety, connection ownership, queued-buffer memory, and remote limits. After completed throughput plateaus, extra in-flight capacity can retain more buffers and connections, oversubscribe executor threads, exhaust resources, or interfere with the trainer and neighboring jobs without delivering more data. Choose the smallest measured concurrency that sustains useful throughput. In-flight task capacity is not physical thread count; already-saturated I/O gains nothing from more overlap, and one additional-parallelism experiment left sample throughput unchanged.
- SPDL reference: {py:meth}`spdl.pipeline.PipelineBuilder.pipe` exposes per-stage `concurrency`. Pass a native async lookup directly, or give a synchronous lookup an executor with a measured thread budget. The setting limits in-flight tasks, not threads, and remains subject to storage and memory limits.

**`serialize_non_thread_safe_client`: protect a client's shared state**
- Trigger: several loader threads use one storage or lookup client in a process, and overlapping operations fail or corrupt its state. A client may maintain a shared connection, cursor, or callback state that cannot safely handle simultaneous access; increasing loader concurrency does not make that client thread-safe.
- Technique: use the client's supported thread-safe variant when available. Otherwise, protect access with a per-process lock so one thread at a time operates on that client's state, while independently owned clients in other processes can still work in parallel. The lock must cover the complete state-sharing operation, not only the initial request call.
- Guards: include callbacks and cleanup in the protection where they share state. Create process-owned clients instead of relying on inherited live connections. Serialization is a correctness measure and may reduce throughput; establish safe behavior first, then measure how much safe concurrency is useful.

**`memoize_deterministic_intermediates`: reuse repeated preparation without freezing randomness**
- Trigger: many records rebuild the same expensive intermediate from a small set of configurations, or repeated preparation/evaluation recomputes identical outputs. For example, a geometry configuration may always produce the same transformation matrix even though each record later receives its own random augmentation. The reusable work is the deterministic part, not necessarily the entire transformed record.
- Technique: cache a deterministic function under a key containing every input that affects its result. A matrix depending on a discrete geometry configuration can be reused for another record with that exact configuration; dtype, device, and versioned settings also belong in the key when relevant. Continue drawing each record's random augmentation parameters independently, and leave randomly drawn intermediates and final augmented records uncached. Retain cached values as immutable, or copy before a consumer mutates them.
- Guards: preserve split boundaries and invalidate changed identities. Bound cache size, publish entries atomically, and fall back on corrupt entries. Verify unchanged per-record random behavior and check that copying a cached value does not erase the benefit. Include cold fill, storage, retention, and replication costs: one case worsened step time, and another reuse analysis found retention/replication costs outweighed the saved computation. Cache hits alone are not evidence of a useful optimization.

**`worker_stable_shard_membership`: let a worker reuse the samples it cached**
- Trigger: loader workers keep private image caches, but epoch reshuffling moves samples between workers. Several workers acquire the same images over time, duplicating storage roughly with worker count while each worker still has poor hits. Changing order within a worker's samples need not require changing which worker owns them.
- Technique: start with the same ordered sample-ID universe on every rank. Build one global permutation with an epoch-independent seed, assign each rank its stride through that permutation, then assign each loader worker its stride through the rank partition. Keep those memberships stable and shuffle only each worker's local list at each epoch, with a seed derived reproducibly from seed, epoch, rank, and worker. Cached samples can then stay with their consuming worker instead of moving with every global reshuffle.

  Send epoch updates explicitly to persistent workers and restore both epoch and local position when resuming. Preserve the existing batch and tail policy; do not introduce padding or sample dropping just to equalize partition lengths.
- Example: this illustrates membership and local order, not a complete distributed sampler. Every participant must use the same `global_order` and topology; `worker_count` counts loader workers within a rank.

  ```python
  import random

  global_order = list(range(12))  # Stable sample IDs in this example.
  random.Random(17).shuffle(global_order)  # Fixed across epochs.

  def local_order(epoch, rank, world_size, worker, worker_count):
      owned = global_order[rank::world_size][worker::worker_count]
      random.Random(f"17:{epoch}:{rank}:{worker}").shuffle(owned)
      return owned
  ```

- Guards: verify full distributed coverage without unintended duplicate or missing samples, the intended shuffle distribution, and deterministic resume. Plumb epoch updates even in deterministic mode. Changing rank or worker counts changes ownership and may invalidate the cache assumptions.

**`atomic_cache_publication`: make complete files visible all at once**
- Trigger: a reader finds a cache filename and assumes the entry is usable, but an interrupted or disk-full write has left only part of its contents. Later reads fail on a corrupt archive instead of treating the data as missing. The final filename should identify a complete entry, not a write still in progress.
- Technique: write the entire encoded entry to a uniquely named temporary sibling on the same filesystem. Validate its expected length or checksum, flush user-space buffers, and close it before atomically replacing the final filename. Readers open only the final name: a reader racing publication sees either the old complete entry or the new complete entry. On write, validation, or replacement failure, remove the unpublished temporary file and preserve the original miss/refetch behavior and any complete old entry.

  If concurrent writers can publish the same key, use an immutable, versioned cache identity so either complete winner has the intended content. Add file and directory synchronization when the cache's required crash-durability contract calls for it; atomic replacement of a name is not itself a guarantee that data survives a crash.
- Guards: test interruption, replacement failure, corruption fallback, and temporary-file cleanup. Failure cleanup was not demonstrated in the source, and interruption/recovery behavior still needs validation. Atomic naming alone does not prove a recoverable cache or crash durability.

**`shared_mmap_catalogue`: share metadata bytes instead of copying Python objects**
- Trigger: a large metadata catalogue is represented as Python objects, such as a list of records containing paths and labels. Each rank or spawned worker constructs its own copy before reading useful payloads, increasing memory and garbage-collection work. Much of that metadata is immutable and need not exist as a separate object graph in every process.
- Technique: store fixed-width numeric columns and variable-width fields in an immutable packed file. For example, place UTF-8 paths in one flat byte region and keep `row_count + 1` offsets; path `i` lies between offsets `i` and `i + 1`. Each offset is a byte position, so the two offsets bound one path without storing a separate Python string for every row. A header records the format version, row count, byte order, field types, and region bounds so readers can validate the layout before indexing.

  Construct or acquire one complete file per host and pass its location and layout metadata to local processes. Each process opens its own read-only memory mapping: it can address the file's bytes without first copying the whole file into its own array of objects, and the operating system can share the file-backed pages. Materialize individual records only when requested; keep subsets and ordering as compact row-index vectors instead of copying or sorting whole tables. Release the original Python catalogue after publication and retain the mapping owner for any returned buffer views.
- Guards: validate offsets, widths, integer overflow, and the intended row universe. Preserve sampling and resume behavior. Keep backing files alive and reopen mappings in each process. Measure shared memory correctly—summing resident memory can count the same shared pages multiple times. Do not substitute source placeholders for measured memory or timing changes.

**`eager_catalogue_row_materialization`: prepare a reusable metadata partition once**
- Trigger: the input path retains columnar metadata but repeatedly extracts a row and converts its values into Python objects whenever that row is visited. A repeatedly traversed partition can incur the same conversion every epoch, producing periodic stalls even when its metadata is already available.
- Technique: identify the bounded partition a worker will reuse, apply the existing filters and column selection, and convert it once into the native row representation the consumer expects. For example, retain a list of tuples containing path, offset, and label, then sample that list by position on later iterations. Leave large media payloads as lazy reads; converting reusable metadata does not require loading the media itself.

  This spends preparation time and resident memory to remove recurring conversion from the hot path. Do not materialize the whole corpus because one partition fits. Treat retained rows as immutable or copy the fields a downstream transform changes so one sample cannot leave state in the next use.
- Guards: bound the partition and measure total host memory with realistic ranks and workers. Preserve nulls, types, order, and filters. An expanded Python object graph can oppose the packed/shared-catalogue strategy above. Reported memory figures disagreed, so they do not establish a precise byte saving or universal feasibility; measure preparation and retention costs together with iteration time.

**`lazy_native_frames_small_detection_cache`: keep small detection images, fetch full frames later**
- Trigger: a video pipeline keeps every decoded full-resolution frame in memory, although detection operates on smaller images and only selected frames need later full-resolution work. The cache pays the full-frame memory cost even for frames that the later consumer never requests.
- Technique: retain the downscaled detection images together with source identity, frame index/timestamp, and the mapping back to each native-resolution frame. Construct those images with the existing resize and color conversion, then run detection on the small cache. Decode or read a full-resolution frame only when a downstream selection needs it, pass it to that consumer, and release it after the work finishes rather than adding every native frame to the detection cache.

  The lazy read must reproduce the selected source frame, not merely the nearest frame returned by a seek. Reduced retained image size can be offset by decoder state or several overlapping full-resolution reads, so include those in the memory budget.
- Guards: preserve selected frames, timestamps, color/layout conventions, and feature outputs. Count temporary buffers, decoder state, and in-flight native frames as well as the small cache. The measured treatment also split stages and included other changes; its time change is not a lazy-read-only estimate.

**`sequential_sampling_for_locality`: read neighboring locations when order can change**
- Trigger: pseudorandom sample order sends successive reads to unrelated files, shards, or offsets, repeatedly discarding useful reader state and cached pages. Some workloads tolerate a storage-aligned sequence, but training that depends on shuffled order may not. This is a change to sample order, not just a different way to read identical batches.
- Technique: derive traversal order from the storage layout, for example shard number followed by row offset, so nearby accesses can reuse open readers, cached pages, or sequential decode work. Keep the same sample universe, record transforms, batch size, and batch/tail policy. Explicitly partition the ordered universe across ranks and save traversal position for deterministic resume.

  Compare the new sequence against the original shuffle using the same data, batch size, and benchmark window. Use it only where learning and evaluation semantics tolerate the changed order; an input-speed improvement is not enough to justify removing needed shuffle.
- Guards: verify distributed coverage, resume, order-sensitive learning, and held-out quality. Do not remove shuffle universally. Keep data, batch, and benchmark scope unchanged when attributing an effect to order.

**`normalized_entity_rows_late_expansion`: store repeated entity histories once**
- Trigger: records describe pairs of entities, such as call participants, and repeatedly contain the same participant history. Storing and preparing a full history in every pair record multiplies bytes and deterministic work, even when those histories are identical for the relevant observation time.
- Technique: separate shared entity histories from the logical pair records. Store each visible history once under an entity-and-version identity; store the pair record as ordered references plus its own labels and attributes. Fetch the referenced histories, reuse identity-stable preprocessing where appropriate, and reconstruct the original pair inputs only when the consumer needs them.

  Logical pairs `(A, B)` and `(A, A)` can refer to one stored history for each of `A` and `B`, but reconstruction must still produce both pairs in order and both occurrences of `A` in the second pair. If history visibility depends on time, the identity must include the required snapshot or cutoff; sharing a later history would expose information unavailable to the original record. Leave stochastic, pair-dependent, and record-dependent transforms after reconstruction unless their equivalence is separately established.
- Guards: preserve pair membership, temporal visibility, filtering, and effective batch semantics. Check mapping completeness, order, and repeated entities. Smaller storage does not prove cheaper lookup, joins, or training. The cited evidence does not isolate a validated training improvement from this representation alone; measure the new access and reconstruction cost.

**`temporal_video_storage_representation`: store nearby frames in video clips**
- Trigger: temporally related video frames are stored as separate image files or raw arrays. Each frame then carries its own storage/request setup, and the representation cannot reuse similarities between nearby frames. A video clip can reduce that repetition, but its compressed layout also changes the work needed to retrieve individual frames.
- Technique: group temporally adjacent frames into clips and build a manifest mapping each sampled frame or window—a requested timestamp interval or consecutive-frame range—to its clip and exact frame index/timestamp. Preserve its annotation association. Choose codec, quality, and keyframe spacing for the actual requests, then open the clip and decode the requested frames or range. Temporal compression can share information between frames and amortize file setup, while a sparse random read may need to decode earlier frames before reaching its target.

  Treat precomputed deterministic resize or other recurring image preparation as a separate representation choice, not an inseparable part of the codec change. Leave stochastic augmentation in training. Compare decoded inputs and downstream outputs against the original representation before accepting lossy encoding.
- Guards: validate compression artifacts, annotations, timestamps, and seeking cost. Temporal compression can hurt sparse random access. Quality checks in one source were limited; later preprocessing fixes removed reported artifacts only for the tested subject. Do not generalize that check or attribute a combined preprocessing/codec treatment to the codec alone.

**`video_subclipping`: reuse short clips with aligned video and supervision**
- Trigger: requested timestamp intervals or consecutive-frame ranges are short, but the input path repeatedly opens and seeks through a long source video to obtain them. Reusable subclips can shorten that work only if their starts are decodable and their frames still align with every associated supervision stream.
- Technique: define one time grid for the source video and supervision, align keyframes to the intended boundaries, and create independently decodable chunks. Copying arbitrary compressed byte ranges does not produce an independent clip. Record each chunk's source interval and source-time origin in its manifest.

  For a chunk starting at source time `t0`, shift retained frame timestamps and every supervision timestamp to `t - t0`. A source frame at 12.4 s in a chunk starting at 10 s has chunk-local time 2.4 s, and its supervision must receive the same shift. Preserve the original boundary-inclusion rule and explicitly handle annotations spanning chunks without silently dropping or duplicating targets. If constant-frame-rate normalization is needed for reliable boundaries, regenerate and validate the source-to-frame mapping afterward instead of assuming the old frame numbers still apply.
- Guards: fractional frame rates broke exact boundaries in the source until constant-frame-rate normalization was added. Check timestamps, frame correspondence, and all supervision streams after normalization. Validate compression/quality effects and count duplicated chunks or bytes as well as decoder savings.

**`file_page_cache_residency_policy`: decide which local file bytes should stay in RAM**
- Trigger: an application reports cache hits because files exist locally, yet repeated reads still access disk. Alternatively, retained file pages compete with the trainer's anonymous memory—memory not backed by files—and contribute to container OOM. The application cache and the operating system's RAM page cache are different layers, so the same logical hit count can describe very different read costs.
- Technique: measure repeated-read disk traffic and file-backed versus anonymous memory under the complete local workload. If a frequently reused set of files fits the host/container budget, use buffered reads that can reuse its pages and keep the files available. An application hot-set policy encourages reuse; it cannot guarantee that the kernel will retain those pages.

  If the working set is too large and one-pass or rarely reused file pages cause memory pressure, test an eviction advisory such as `POSIX_FADV_DONTNEED` after consumption at a suitable point in the read/write lifecycle. Apply it only to the intended files or ranges, then measure latency, reclaim, and memory. Retaining useful pages and discarding low-reuse pages are opposite interventions for different workloads, not interchangeable ways to increase a cache-hit counter.
- Guards: budget file and anonymous memory across all local ranks and workers. Advisory eviction may not be immediate and can block on some paths, so validate where it is issued. A higher logical hit rate does not prove RAM residency, and a residency policy must fit the whole workload rather than one reader in isolation.

**`row_group_statistics_pruning`: skip blocks that cannot contain a match**
- Trigger: storage organizes table records into blocks or row groups, but the reader fetches and decompresses every group before rejecting most records with a known filter. If the group metadata can prove that no record matches, those payload reads and decompressions are unnecessary.
- Technique: read the manifest or footer containing group byte locations and conservative column statistics before requesting payload ranges. Use those statistics only to prove exclusion. For `x >= 10`, a trustworthy group maximum below 10 proves the group cannot match; a minimum below 10 does not. For a conjunction, one impossible clause rejects the group; for a disjunction, every branch must be impossible.

  Read surviving groups in their original order and still apply the full predicate to their records. Missing or unusable statistics, uncertain null/NaN semantics, or incompatible comparisons mean the group may match and must be read. Pruning saves work only when exclusion is certain; it is not a replacement for the row filter.
- Guards: missing, null, or overlapping statistics must fall back to reading. Preserve record order, predicate semantics, and required error behavior. Uncertainty in metadata is not permission to omit records silently.

**`shared_source_frame_filter_views`: share one metadata table among filtered datasets**
- Trigger: several datasets in one process read the same metadata table, then retain separate full-table copies to select different records. Only the selections differ, but the process pays for the source metadata repeatedly. Despite the stable ID's name, this entry concerns a metadata table, not decoded video frames or memory sharing across training ranks.
- Technique: read the metadata table once and keep it read-only. Give each filtered dataset a reference to that same table plus its own selected row numbers or mask. A dataset-local index selects a row number from its list, which points back to the source table; it does not require another table copy. For example, datasets selecting source rows `[0, 2]` and `[1, 2]` keep separate selections while both refer to the same source row 2.

  Share only the same immutable table with the same schema and field-conversion settings. Key reuse by the source/table identity (or version-pinned source location), together with table version, schema and conversion settings. Different tables can have the same version number, so version alone must not select the cached copy.

  Build selections with the original cast, null, and filter-order rules. Use an ordered row-index vector when dataset-specific ordering or duplicates must be represented; a simple mask cannot express every such selection. Keep each dataset's mutable state outside the read-only table, and retain the table owner until its last view is gone.
- Guards: preserve table version, schema, conversions, cast/null semantics, filter order, ordering, and duplicate positions. Do not mutate the owner through a view. Sharing a table load can also share its failure: preserve the intended source-load error handling and keep dataset-specific errors attributed to the correct dataset. Account for retained originals and view overhead. This shares metadata within one process only; it makes no cross-rank memory claim.

**`episode_locality_with_shuffle`: shuffle video chunks, read nearby frames together**
- Trigger: training samples video frames from many episodes, where an episode is a recorded sequence/video with associated annotations. Uniformly random frame order repeatedly switches videos or seeks to distant frames, disrupting video-reader cache locality. Fully sequential training may be unsuitable, so the goal is to retain shuffle while avoiding a reader switch for every frame.
- Technique: enumerate each episode's valid sampled frames in temporal order and divide them into deterministic consecutive-frame chunks. The chunk size specifies how many consecutive entries from that valid frame sequence are read together; preserve the existing policy for the final partial chunk. Represent each chunk by episode identity and its ordered frame indices or range. At each epoch, reproducibly shuffle the global chunk list, partition it deterministically across ranks, and emit frames in order within each assigned chunk. Nearby reads can reuse video reader/decoder state while the order of chunks changes between epochs.

  Preserve per-frame augmentations and the sample universe. Save both chunk position and position within the chunk for resume. Compare consecutive-frame chunk sizes with the same batch/tail policy: larger chunks change the temporal correlations and batch composition seen by training, not merely decode efficiency.
- Guards: check distributed coverage, diversity, batch composition, and deterministic resume. Promote only after quality checks on the changed sample-order correlations. Count decoder/cache memory as chunk size grows. The mechanism here is video-reader locality, not a general claim about every sequential input source.

**`persistent_pid_owned_manifest_handles`: open a random-read manifest once per process**
- Trigger: every record lookup reopens a large manifest and repeats file or reader setup before reading a small range. The bytes needed for each record are already described by offsets, so repeated open/setup work can dominate otherwise simple reads. A reused handle must still belong to the process using it and support safe access by that process's threads.
- Technique: serialize only a lightweight descriptor with the immutable manifest location and each record's byte offset/length, not a live handle. On the first read in a process, open the file and record its owning PID. Reuse it for later records; if the PID changes, discard the child's inherited handle and reopen a child-owned one.

  For a plain offset-addressable file, positional reads such as `os.pread(fd, length, offset)` avoid a shared seek cursor; handle short reads by looping or failing according to the input contract. For a stateful format reader, synchronize the complete seek/read/decode operation or use independently owned readers. Validate each range and close process-owned handles during teardown. This changes handle reuse, not the bytes defining a record.
- Guards: respect descriptor limits, backing-file lifetime, and thread safety. Validate offsets and file/format boundaries, close explicitly, and never share an unsynchronized seek cursor across threads or processes.

**`intra_frame_storage_random_access`: reduce video frames decoded before a sparse target**
- Trigger: sparse random video requests ask for isolated frames from a temporally compressed stream, such as H.264. Some pictures store their own image information; others depend on pictures decoded earlier. Reaching a target can therefore require starting at an earlier safe random-access boundary and decoding many frames the consumer never uses. A generic keyframe/I-frame flag does not guarantee that following frames are independent of everything before that boundary.
- Technique: profile requested frame positions and the preceding decode work. Compare an all-intra layout, where every frame is encoded independently, or shorter intervals between suitable random-access boundaries. For the latter, use boundaries whose following group of pictures does not depend on earlier pictures—for example appropriate H.264 IDR or closed-GOP boundaries—not merely more frequent frames labelled as keyframes. Keep the stream/container metadata needed to initialize decoding. These layouts can start decoding closer to the target, but generally give up some temporal compression. Update the manifest while preserving requested frame/timestamp and annotation mappings, then verify the same sparse requests and decoder outputs against the original clip.

  Choose using decode work, encoded size, encoding cost, and expected access frequency/reuse. There is no universally best codec or keyframe interval, and a size tradeoff measured on one clip need not hold for other content or access patterns.
- Guards: measure storage and encoding costs as well as decode savings. Validate pixels or acceptable compression quality, timestamps, and annotation equivalence. A sparse-access improvement can lose to temporal compression during sequential traversal.

**`chunkwise_cache_scan`: parse a byte stream without assembling the whole file**
- Trigger: a cached JSON-lines reader receives ordered byte chunks but joins them into one large allocation before looking for lines. Checksum work may then revisit that concatenated buffer. Most lines could be parsed as they arrive, without retaining another full-file copy.
- Technique: scan newline boundaries in each chunk and pass complete lines to the existing JSON parser. Retain only the unfinished suffix and join it with the next line fragment when a line crosses a chunk boundary. At end of input, apply the original final-line rule. Scanning byte newlines and decoding complete lines preserves UTF-8 characters split across chunks; a streaming text decoder is another option if it retains incomplete code points. Bound or reject overly long lines according to the original contract.

  Compute the checksum over the original byte stream as well. If the algorithm provides an exact combine operation, retain each chunk's checksum and byte length and combine them in order; otherwise update one streaming checksum as chunks arrive. Adding, XORing, or concatenating digest values is not a substitute for the original stream's checksum.
- Example: chunks `b'{"x":1}\n{"x":'` and `b'2}\n'` contain two records. Only the unfinished `b'{"x":'` joins the next line fragment, not the whole file. Checksum input still includes every original newline byte even if the parser strips it.
- Guards: preserve UTF-8 decoding across split code points, line boundaries, ordering, final-line behavior, and malformed-input behavior. Verify exact checksum equivalence; combining checksums requires lengths and the correct algorithm, not merely numeric digest values.

**`bounded_reusable_media_cache`: reuse video files and readers with separate budgets**
- Trigger: repeated video windows—requested timestamp intervals or consecutive-frame ranges—redownload the same video file or reopen its reader/decoder. Reusing these resources can avoid setup, but an unbounded per-worker cache can exhaust memory. Downloaded files, live readers, and decoded frames are different retained objects: caching one does not establish a safe budget or lifetime for the others.
- Technique: use immutable video identities to reuse local downloaded files, with a disk-space and retention policy separate from the reader cache. Maintain a process/worker-owned least-recently-used map of reusable video readers/decoder state, keyed by video identity and compatible decoder settings. On a hit, mark the entry recently used and safely seek/reset it for the requested interval; reopen it when its state cannot be safely reused. On a miss, acquire/open it once and admit it within the cache's bound. Preserve the requested video-to-annotation alignment rather than assuming that any nearby decoded frames are equivalent.

  A reusable reader may have a mutable seek position and decoder buffers. Unless its API explicitly supports concurrent requests, protect the whole seek/reset/decode operation with an exclusive lease or lock, or use independently owned readers for simultaneous requests. A second request must not reposition a reader while the first is decoding.

  Separately, retain a lifetime lease or reference while a request is active. Reference counts prevent eviction or freeing; they do not make mutable reader state thread-safe. Evict the least-recently-used eligible reader only when no caller still uses it, then close it and release its retained resources. A downloaded file must also remain available for readers that depend on it. Track decoded-frame buffers separately and release them when their consumers finish: closing a reader need not free frames still held elsewhere. Entry counts can bound admission, but variable file sizes and decoder footprints may require byte accounting or another tested resource bound.
- Guards: count downloaded-file storage, open readers/containers, decoder state, live decoded frames, and outstanding references across all ranks and workers. If entries remain leased, do not invalidate them just to satisfy an entry limit; keep admission within a safe resource policy. Validate close, seek, reset, and reopen behavior, exact requested frame outputs, and video/annotation alignment. Capacity in entries is not a byte bound. A short survival check is not proof that a full run is leak-free.
