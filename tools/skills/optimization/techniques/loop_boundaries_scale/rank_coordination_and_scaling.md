# Rank coordination and scale

These techniques cover rank-side diagnostics, control synchronization, process-group setup and data-parallel GPU allocation. Open this topic when rank 0 delays collectives, debug or loader-control waits expose overhead, setup creates redundant groups, or available input capacity leaves GPUs underused.

[Catalog index](../../technique_catalog.md) · [Training-loop boundaries and scale](../loop_boundaries_scale.md)

**`rank0_side_work_off_critical_path`: keep rank-0 side work off the step path**
- Trigger: rank 0 straggles (its forward or data time far exceeds other ranks') and the others block at the next collective. Traces show TensorBoard flushes, histograms, progress writes, or a stats collective inside the loader's `next()`.
- Technique: enqueue immutable log/progress/output records to a bounded background writer instead of doing per-step side I/O on rank 0 before its next collective. Sample expensive histograms every N steps, and schedule loader-stats all-gathers only at a logging interval shared by every rank. Snapshot values at the intended step rather than letting the writer read later-mutated model or buffer state. This lets rank 0 rejoin compute sooner while limiting diagnostic work; it does not make collective participation asynchronous.
- Guards: do not move logging collectives to a thread: collective order must stay deterministic, so throttle them instead. Keep per-step logging that needs no collective. Preserve record order, buffer ownership, backpressure and error reporting, and drain writers at shutdown; do not retain live computation graphs in queued records.

**`remove_debug_device_syncs`: make debug synchronization opt-in**
- Trigger: timing or diagnostic code synchronizes the device in every phase.
- Technique: identify synchronization used only to time or materialize diagnostics, and gate it behind an explicit debug option rather than forcing every training phase to finish on the host. Keep GPU-event timing for completed device work separate from host enqueue timing. Timestamp batch readiness and consumption separately from producer stalls: a batch can be old because it waited in a ready queue, not because the producer is currently late. Removing diagnostic waits restores overlap; it does not remove dependencies needed for correct execution.
- Guards: retain required stream/copy dependencies and completion waits before buffers are reused or outputs read. The profile's scope changes once syncs are gone; an unsynchronized host duration is not device execution time. A full queue does not prove main-thread headroom.

**`single_rank_input_sync_fastpath`: skip input rank synchronization at world size one**
- Trigger: a single-trainer job runs an end-of-data synchronizing iterator with a collective and one-deep prefetch although no peer ranks exist.
- Technique: branch on training world size when constructing the iterator. At world size one, use the local iterator's end-of-data result directly instead of exchanging availability flags through a collective, and allow a bounded queue of ready batches rather than one-deep lookahead. Return the same local batch sequence and terminate on its local end of data. There is no peer rank whose exhaustion decision needs agreement, so the control round trip is redundant.
- Guards: one trainer means one rank, not one loader worker. Restore synchronization when scaling out. Local copy completion is still needed, as are buffer ownership and propagation of loader errors.

**`reuse_distributed_setup_group`: reuse an existing process group for loader control**
- Trigger: loader setup creates an extra distributed process group only for control messages.
- Technique: pass an already initialized, compatible process group into loader control instead of creating another group during setup. Require the same participating ranks and support for the control message tensors/operations on that backend. Reuse avoids rendezvous and communicator creation; it changes neither the messages nor their per-batch frequency. Keep a separate group when independent ordering, backend or lifecycle requirements make sharing unsafe.
- Guards: this does not remove per-batch synchronizing collectives. Caller semantics for group usage must stay correct: every participating rank must issue collectives in the same order, including other users of the shared group, and the loader must not destroy a caller-owned group.

**`fewer_gpus_same_global_batch`: use fewer GPUs at the same global batch**
- Trigger: after loader fixes, host CPU and memory have headroom and per-GPU throughput is the cost driver, or the input rate cannot keep the allocated GPUs busy. Fewer data-parallel ranks may use available input capacity more effectively, but each remaining rank must process more samples per update to preserve the global batch.
- Technique: compare fewer data-parallel ranks with a proportionally larger local batch while preserving the model recipe's effective global batch. Without accumulation, `global_batch = ranks * local_batch`; include the accumulation factor when it is used. For example, four ranks with local batch `b` and two ranks with local batch `2b` process the same number of examples per update only if the rest of the update schedule is unchanged. Retune worker count and I/O concurrency for greater demand per remaining rank, and verify that total reader capacity has not fallen automatically with GPU count.
- Guards: preserve optimizer semantics and updates, scheduler, negatives per batch, normalization statistics, gradient accumulation, sample coverage and quality. Larger local batches change memory, kernel shapes, normalization and random/order behavior, so constant global batch alone is insufficient. Do not count a changed-global-batch run as validation: reducing global batch caused repeated held-out quality regressions in one comparison despite fewer GPU-hours. Attribute combined input and model changes separately; some fewer-GPU results bundled preprocessing, compilation or reduced precision, and numerical-quality checks were limited rather than exhaustive. Include measured resource duration and cost from completed runs. Do not reduce model-parallel groups or other topology axes under a data-parallel batching rule. More samples per GPU alone does not establish a faster or cheaper completed run.
- SPDL reference: Retune the existing {py:class}`spdl.pipeline.defs.ProcessPoolExecutorConfig` worker count and {py:meth}`spdl.pipeline.PipelineBuilder.pipe` concurrency as separate knobs after rank topology changes. SPDL does not preserve global batch or quality on behalf of the trainer; the original model recipe and matched full-run validation remain the reference.
