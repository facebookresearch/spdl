# Buffering and sample mixing counterexamples

This topic covers decoded-episode buffers, worker-local packing and ready-queue capacity. Open this topic when more retained data or a different mixing topology promises better diversity or delivery but adds memory cost or changes training behavior.

[Catalog index](../../technique_catalog.md) · [Negative results](../negative_results.md) · {ref}`Compare loader implementations <compare-loader-implementations>`

**`byte_budgeted_episode_shuffle`: decoded-episode buffering trades host memory for batch diversity, not speed**
- Trigger: Each loader worker processes only one episode at a time. An episode is a source sequence, such as a video or audio recording, from which the loader draws sample windows. A worker emits all windows from its current episode—for example, overlapping clips from one video—before moving to the next. As a result, batches may contain samples from only a few distinct episodes. Keeping several decoded episodes open can improve mixing, but a fixed episode count does not bound memory because their decoded sizes vary.
- Attempt: Use a dataset-level default-off buffer, explicitly enabled by recipes that need episode diversity. Sample uniformly among open decoded episodes, replace an episode only after emitting all its windows, and permute window order within each episode. Limit admission by both a per-worker byte budget and a maximum episode count, whichever binds first. This admits more short episodes and fewer long ones. Buffering decoded episodes avoids repeatedly decoding frames shared by overlapping windows. Keep cached frames at native resolution and upscale individual windows later.
- Outcome: Adopted for batch diversity at the cost of more host memory. Do not assume a steady-state speed benefit.
- Guards and when to revisit: Budget across all worker processes on a node: ranks per node × workers per rank. Typical additional memory is approximately (open episodes − 1) × workers per node × mean decoded episode size; also check worst-case sizes. Fit both baseline and buffered footprints within the job's enforced memory cap, not just physical node RAM: disabling the buffer does not guarantee the baseline fits that cap. The relatively compact decoded cache depends on retaining native-resolution frames; caching after upscaling increases the decoded-to-encoded size ratio and can invalidate the memory estimate. Admit an episode larger than the entire byte budget when necessary to make progress, so the budget has an explicit oversized-item exception. Interleaving invalidates seeds tied to emission order; use episode-based seeds and expect changed random augmentation masks when the affected augmentation is enabled. Finite-stream tests covered within-batch interleaving, exact once-per-epoch coverage, determinism and budget bounds. Such coverage does not make a prefix of an epoch-overlapping live stream a complete epoch. A short single-node training screen does not establish convergence, a quality benefit from diversity or general throughput behavior; end-to-end recipe configuration still requires validation. A faster first iteration with an unexplained cause is not evidence of a repeatable startup or throughput benefit.

**`worker_local_packing_quality_gate`: worker-count changes can alter training behavior**
- Trigger: Packing combines several short samples into one larger input so less space is wasted on padding (for example, putting two short token sequences into one fixed-size block). A change in worker count can alter which samples each worker packs together and the order in which those packs reach the optimizer, even if the overall dataset mixture or aggregate loss matches.
- Attempt: Increase the number of workers that pack examples while keeping the overall dataset mixture.
- Outcome: The larger worker increase hurt model quality: the model answered far fewer evaluation prompts with the requested number of items, even though the overall dataset mixture, training loss and gradient norms were similar. The smaller increase largely preserved that ability. With worker-local packing, changing worker count changes the sample streams: different examples can survive filtering, end up in the same pack, or reach the optimizer in a different order. The comparison did not isolate which of those differences caused the quality drop or show that padding cost was responsible. Do not generalize the tested worker counts to another dataset or training duration.
- Guards and when to revisit: Retry with fixed worker topology during quality validation, explicit local-distribution and ordering checks, and a passing task-quality comparison; tune reader threads independently where possible. Reader threads that feed an unchanged packing topology are a separate concurrency hypothesis, not evidence that extra packing workers preserve behavior. Preserve optimizer order, effective batch and worker-local mixtures. There is no universal safe worker cutoff. More tokenizer threads can also reduce rows/s; extra concurrency is not equivalent to extra throughput.

**`well_fed_transport_change_negative`: more sink capacity was not pursued while boundary queues were already fed**
- Trigger: Output queues (sinks) at a process boundary already hold ready batches on most ranks, and a larger sink or shared-memory transport is proposed to close a remaining throughput gap.
- Not tested: A larger sink or shared-memory transport in the already-fed comparison. The least-fed rank had a nearly empty final ready queue in long runs, and it was unclear whether extra capacity could help.
- Related outcomes: In a separate data-delivery-bound comparison, increasing only the final sink depth gave a modest training gain consistent with absorbing slow-rank and pinned-memory delivery variability. That queue-depth-only change was accepted without a separate quality gate because it preserved sample semantics. In another comparison, building batches directly in shared memory removed a measured private-to-shared copy, improved training throughput and passed its accuracy gate. A different shared-output slot reuse change improved throughput but still had tail-rank starvation and mixed evaluation results. In one test, running the loader slowed the trainer despite always-ready batches; the test did not isolate interpreter-lock (GIL), CPU or memory contention.
- Guards and when to revisit: If the producer is consistently faster than the consumer, the sink tends to stay full. If it is consistently slower, extra capacity only delays the sink draining. When their rates are close, extra depth can absorb short delivery gaps and stabilize throughput. Before changing capacity or transport, establish a measured copy cost, slowest-rank starvation or delivery variance a buffer can absorb; then compare complete-path performance, memory and quality. The well-fed decision has limited comparison scope: different GPU allocations were measured at different times using remote data access. Re-measure on the intended execution location rather than treating that decision as placement-independent. Report occupancy as the minimum across ranks over time, not an average. A full queue shows ready inventory, not throughput or absence of trainer contention. Bound shared-memory buffers per rank, count retained slots, and check sample semantics and model quality before adopting a transport change.
