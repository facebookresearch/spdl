# Trainer pauses and communication counterexamples

This topic covers distributed communication tuning and optional forced garbage collection. Open this topic when changes on the synchronized trainer path promise better overlap or shorter tails without a matched training win or a diagnosed recurring pause.

[Catalog index](../../technique_catalog.md) · [Negative results](../negative_results.md) · {ref}`Compare loader implementations <compare-loader-implementations>`

**`distributed_model_tuning_negative`: communication-setting changes lost the tested training comparisons**
- Trigger: After major input or CPU bottlenecks are reduced, profiles show communication taking a larger share of step time, and data-parallel communication settings such as gradient bucket size, static-graph mode or gradient bucket views are proposed as a speed lever. Reduced input starvation does not establish that every rank is fully fed.
- Attempt: Change reduction bucket size, enable static-graph mode or enable gradient bucket views separately. Reduction buckets group gradients for collective communication; size changes collective frequency and overlap with backward compute. Static-graph mode assumes an unchanged training graph, while bucket views let gradients alias communication-buffer storage to avoid copies.
- Outcome: In one set of comparisons, smaller and larger reduction buckets, static-graph mode and gradient bucket views were tested separately against the default, and all were slower. In another tested case, a smaller bucket cap made the first bucket ready earlier in an exact reducer proxy with identical gradients, yet the two warm training epochs were slower; only the cold epoch improved. No common cause of the slowdowns was isolated.
- Guards and when to revisit: Retain the defaults unless a new matched training comparison wins. Start from a steady-state multi-rank trace showing exposed communication, then vary one setting at a time and require correctness and quality checks. Such a trace is a prerequisite, not proof of benefit: a smaller-bucket treatment regressed despite substantial exposed communication. Preserve distributed topology, global batch and gradient semantics. Earlier readiness in a proxy is not a training gain. The smaller-bucket screen used one control/treatment pair, stopped after one cold and two warm epochs, without long-run or held-out quality validation. Training loss matched exactly in the first warm epoch and gradient-norm differences were at noise level: the slowdown was not accompanied by an observed training-correctness failure. Match controls by execution location and use the default control for that location; one result combined locations, so it does not establish location-independent behavior. The smaller-bucket result concerns a gradient set that fit in one default bucket; do not assume the same tradeoff for much larger gradients. The broader sweep supplied no model-quality data, so rerun quality gates for the exact intended configuration. GPU allocation and loader configuration were unspecified for that sweep, limiting transfer to a retuned setup.

**`forced_gc_without_tail_negative`: do not add periodic forced collections without a measured GC tail**
- Trigger: Periodic forced garbage collection, such as a full collection in the trainer every N steps, is proposed as a tail-latency fix, but telemetry shows neither a recurring steady-state pause from automatic collection nor unexplained late output-queue spikes.
- Not tested: Periodic full collections during training. In separate pipelines, one prerequisite check found no recurring steady-state GC tail, and another found no unexplained late output-queue spikes. The latter ran an isolated full collection and observed a substantial pause. As a trainer callback, that work pauses synchronized training ranks without collecting objects in separate loader worker processes. Adding a visible pause is unjustified without evidence that it removes a larger one.
- Guards and when to revisit: First show a recurring pause, or memory growth from reference cycles, in the process where it occurs. Then compare collection count and duration, memory and completed steps against a matched control, and collect only at supported quiescent boundaries (see the [GC guide](../../gc_optimization.md)). This entry concerns pauses added without a diagnosed purpose. General safety guidance: a collection that fixes a diagnosed problem, such as reference cycles retaining batches until memory runs out, is a separate decision. Keep correctness-required collections, and restore changed GC settings on exit and failure. In synchronous training, a pause on one rank stalls all ranks.
