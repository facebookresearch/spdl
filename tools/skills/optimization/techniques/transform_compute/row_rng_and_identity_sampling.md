# Row RNG and identity sampling

These techniques cover per-row random seeds and fallback identity draws. Open this topic when worker assignment changes augmentation draws or identity-pool scans dominate sampling.

[Catalog index](../../technique_catalog.md) · [Transform compute](../transform_compute.md)

**`per_row_cpu_generator_seeding`: seed each row's augmentation independently of worker assignment**
- Trigger: augmentations draw from worker-local streams, so changing which worker processes a row changes its draws even when sampler order is unchanged.
- Technique: assign entry, epoch, step and within-step position before dispatch, then derive a deterministic per-row seed from those coordinates and the run seed with a stable mixing function such as splitmix64. Mix in rank to keep distributed augmentation streams distinct. Immediately before transforming each row, reseed the RNGs its transforms actually use: for example, the process-global Python `random`, NumPy and torch CPU generators, rather than a dedicated generator passed to each operation. Return asynchronously completed batches in step order. Reconstruct sampler order and consumed-step position on resume so the same coordinates reproduce the same draws.
- Guards: global reseeding and the associated transform must not interleave with another transform using those same process-global RNGs. Include every random library used; seeding torch alone does not control Python or NumPy draws. Omitting rank from the seed correlates augmentation draws across ranks. When adding rank to an existing mapping, rank 0 can keep its old mapping while rank is mixed in for the other ranks. Per-row seeding changes draws relative to baseline worker streams: in one tested case repeatability and resume tests passed, but batches were not bit-identical to the baseline, and short loss comparisons only placed differences within seed noise. Preserve entry/epoch/step/position and repeated-row semantics across dispatch and resume. This is reproducibility guidance, not an isolated throughput claim.

**`constant_time_identity_sampling`: avoid full-pool scans in fallback sampling**
- Trigger: fallback negative sampling linearly scans a large identity pool on each sample.
- Technique: build a randomly indexable pool once, preserving the baseline's sampling unit (unique identities or entries with duplicate multiplicity). For each fallback draw, sample uniformly from that pool and retry while the identity is excluded. This produces the uniform distribution conditioned on acceptance without building the allowed list on every draw. For example, rejecting A and C from a uniform pool [A, B, C, D] leaves B and D equally likely. Expected cost is constant only when the accepted fraction stays bounded away from zero. Use a bounded retry policy with an exhaustive, distribution-preserving fallback when acceptance is low; choosing the first allowed identity would bias the result.
- Guards: preserve curated negatives, exclusion rules, duplicates and RNG behavior. For sampling without replacement, update exclusions after each accepted draw. Handle singleton or nearly exhausted pools without infinite loops, including the no-valid-negative case. Rejection usually consumes different RNG draws than scanning and indexing an allowed list; if identical seeded outputs are required, distributional parity alone is insufficient. Distributional equivalence requires a sampling test, not just matching a few output values; measure pool-building cost separately.
