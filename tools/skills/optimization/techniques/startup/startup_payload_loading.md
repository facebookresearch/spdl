# Startup payload loading

These techniques cover immutable backing descriptors, independent manifest decoding and lazy evaluation sources. Open this topic when worker bootstrap copies large dataset payloads, serial manifest decoding delays startup, or eager evaluation construction loads data that will not be consumed.

[Catalog index](../../technique_catalog.md) · [Startup](../startup.md)

**`spawn_mmaps_by_descriptor`: send backing references instead of dataset bytes**
- Trigger: spawned workers receive entire memory mappings or large record graphs through serialization, multiplying payload, startup memory, and pipe traffic. For example, PyTorch `DataLoader` with the `spawn` start method serializes the `Dataset` to each worker. An eagerly built dataset can therefore make startup slow even when the samples themselves are small.
- Technique: make the serialized dataset state a small description of immutable backing storage rather than the mapped contents or expanded Python rows. Carry the file location and version identity, byte offset/length, dtype/shape or record-index layout, and the subset information needed to reconstruct the same dataset. Exclude live mappings, file handles, and clients from that serialized state. Inside each child, validate the descriptor against the backing file, open a child-owned handle, and create a read-only mapping or indexed reader; map from an alignment-valid offset and expose the intended subrange when the mapping API requires it. Retain the file and mapping owners until all consumers and views are released. Use a type-specific serialization hook or explicit descriptor object, not a global reducer that changes unrelated values. The worker still reads the same bytes, but bootstrap transfers references and layout metadata instead of repeatedly transmitting the payload.
- Example: a fixed-width integer array can be described by `(path, version, byte_offset, element_count, byte_order, element_width)` rather than a list of its values. For variable-width records, carry the validated offset-table layout as well; shape alone cannot reconstruct the record boundaries.
- Guards: keep files valid until every consumer releases them, reopen process-owned handles after PID changes, scope reducers to intended types, and clean up temporary backing files. Preserve row identity and immutable sharing. A forkserver variant may hang; changing the process method is not required for descriptor serialization.
- SPDL reference: when profiling shows eager dataset construction or worker serialization dominates startup, prefer building the source around small descriptors with {py:class}`spdl.pipeline.PipelineBuilder` instead of passing a materialized dataset to spawned workers. The descriptors must stay small regardless of which loader runs them.

**`parallel_independent_decode_units`: decode independent manifest groups in parallel**
- Trigger: a compressed manifest delays startup because independent row groups are decoded serially.
- Technique: obtain a manifest/index describing each independently decodable group's ordinal, compressed byte range, schema, and expected row count. Schedule group descriptors through a bounded executor; each task opens its own reader or consumes its own immutable input slice, decodes one group, and returns rows tagged with that ordinal. Reassemble groups in manifest order rather than completion order, and apply the original row conversion and error handling. Use threads only when the decoder can execute concurrently without unsafe shared state and, for CPU-bound work, releases the GIL; otherwise assess process workers with descriptor-sized inputs. Bound both executing tasks and decoded results awaiting ordered assembly. Arbitrarily slicing one compressed stream does not make independent groups: if a group requires dictionaries or state from an earlier group, retain that dependency or use the serial path. This overlaps decode work while leaving acquisition and final assembly as separately measured costs.
- Guards: do not share an unsynchronized file-like cursor. Verify that groups are genuinely independent and preserve row count, order, types, and error handling. Bound CPU and decompressed-buffer memory; parallelism cannot remove remote acquisition or final assembly costs.

**`lazy_budgeted_eval_source`: stream only the evaluation prefix that will be consumed**
- Trigger: evaluation construction eagerly materializes corpus-scale splits before training even though each evaluation cadence consumes only a small, explicit batch budget.
- Technique: resolve shard paths without loading their payloads, then use a finite, single-pass source that reads batches lazily as evaluation consumes them. For Parquet, `ParquetFile.iter_batches` can retain the same per-sample processing and batched output fields while bounding resident payload memory by a read batch rather than corpus size. Emit full batches in source order and apply an explicit trailing-batch policy; one tested implementation dropped a short tail. If shuffling shards, shuffle once at construction with a seed derived from the base seed and process index. Rebuilding with the same seed and process assignment each cadence reproduces that process's sample prefix. Stop consumption at the evaluator's batch budget rather than reading the remaining corpus.
- Guards: unchanged per-sample processing does not imply unchanged sample selection. In one tested case, seeded shard shuffling changed the selected subset and the evaluation budget increased at the same time. Keep selection, seed/process assignment, batch size and tail policy explicit; compare lazy and eager implementations at the same budget to isolate loading effects. Metrics from different subsets need not be comparable. Report evaluation latency as well as time to first training step: needed reads are deferred, while unused reads are avoided. Startup improvement and matching sample-processing logic alone do not validate final loss or per-domain evaluation quality; those outcomes remained unvalidated in that test.
